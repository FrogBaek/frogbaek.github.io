## 들어가며

하나의 작업이 원자적으로 끝나는 경계를 어디에 둘 것인가. 이 질문을 들고 코드베이스를 한 바퀴 돈 기록입니다.

MySQL 의 기본 격리수준인 REPEATABLE READ 에서 READ COMMITTED 로 한 단계 낮추기로 한 판단과, 그 과정에서 식별한 동시 수정 네 가지 사례(카운터 증가, 상태 전이, 있으면 UPDATE 없으면 INSERT, 같은 이벤트가 두 번 도착하는 경우)를 어플리케이션 코드에서 어떻게 보호했는지 정리했습니다.

스프링을 처음 써 보면 누구나 한 번쯤 닿는 결론이 있습니다. "메서드에 `@Transactional` 만 붙이면 동시성 문제는 알아서 해결된다." 나도 그랬는데, 이번 작업을 하면서 그 결론이 어디까지 맞는지를 직접 따라가 본 기록이 이 글입니다.

## 1. "원자적으로 끝난다" 가 정확히 뭘 보장하는가

`@Transactional` 이 실제로 해 주는 일은 두 가지입니다.

1. **롤백 단위**. 메서드 안에서 예외가 나면 그 안의 DB 변경이 한 번에 되돌려집니다.
2. **격리수준 적용 범위**. 메서드 안에서 보는 데이터는 설정한 격리수준의 규칙을 따릅니다.

여기서 빠진 게 하나 있습니다. **두 트랜잭션이 같은 row 를 동시에 만질 때 자동으로 줄을 세워 주는 일** 은 안 합니다. 그 일은 격리수준이 일부 떠맡고 있는데, 격리수준에 따라 어디까지 떠맡는지가 달라집니다.

예를 들어 사용자가 혜택을 클릭할 때 조회 수를 +1 하는 코드를 보겠습니다.

```java
@Transactional
public void increaseViewCount(long benefitId) {
  Benefit b = benefitRepository.findById(benefitId).orElseThrow();
  b.setViewCount(b.getViewCount() + 1);
  // @Transactional 종료 시 flush → UPDATE
}
```

`@Transactional` 이 붙어 있으니 직관적으로는 안전해 보입니다. 그런데 두 사용자가 같은 혜택을 거의 동시에 클릭하면 이런 순서가 나옵니다.

![](/images/6/transaction_boundary.png)

- T1: benefit 조회. viewCount = 10
- T2: benefit 조회. viewCount = 10
- T1: setViewCount(11)
- T2: setViewCount(11)
- T1: 커밋. `UPDATE benefit SET view_count = 11 WHERE id = ?`
- T2: 커밋. `UPDATE benefit SET view_count = 11 WHERE id = ?`

두 번 클릭했는데 카운터는 한 번만 증가했습니다. **한쪽 변경분이 통째로 사라지는 현상** 의 가장 기본적인 형태입니다. `@Transactional` 안에서 일어났는데도 막히지 않았습니다. 메서드 안의 두 줄 사이에 다른 트랜잭션이 끼어들었기 때문입니다.

여기서 첫 질문이 떠올랐고, 이게 이번 작업 전체의 출발점이 됐습니다.

> **이 두 줄이 정말로 "한 덩어리" 로 끝나려면, 그 경계를 어디에 두어야 하는가.**

선택지가 몇 개 있습니다.

- **DB 격리수준에 맡긴다**. DB 가 자기 락 시스템으로 두 트랜잭션을 줄 세워 주길 기대한다.
- **JPA 의 비관락 (`SELECT ... FOR UPDATE`) 을 건다**. 조회 시점에 row 락을 미리 잡는다. 다른 쪽은 락이 풀릴 때까지 기다린다.
- **JPA 의 낙관락 (`@Version`) 을 건다**. 충돌은 사후에 알고, 재시도하거나 사용자에게 알린다.
- **조회를 빼고 단일 SQL 로 바꾼다**. `UPDATE ... SET view_count = view_count + 1 WHERE id = ?`. DB row 락 한 번에 의존한다.

이 글은 케이스마다 그 네 선택지 중 무엇을 골랐고 왜 그걸 골랐는지 정리한 기록입니다. 그전에, "DB 격리수준에 맡긴다" 가 그동안 알게 모르게 기대 온 길이었다는 얘기부터 짚고 가겠습니다.

## 2. MySQL 의 REPEATABLE READ 가 공짜로 해 주던 것들

MySQL InnoDB 의 기본 격리수준은 REPEATABLE READ (이하 RR) 입니다. PostgreSQL 의 기본이 READ COMMITTED (이하 RC) 인 것과는 다릅니다. 그래서 Spring Boot + MySQL 조합으로 별다른 설정 없이 출발한 프로젝트는 처음부터 RR 위에서 돌고 있습니다. 이 프로젝트도 그랬습니다.

RR 이 정확히 해 주는 일은 두 가지입니다.

**1. 트랜잭션 안에서 본 row 의 값이 끝까지 그대로 보인다.**

트랜잭션을 시작한 시점에 찍은 스냅샷이 그 트랜잭션이 끝날 때까지 유지됩니다. 같은 row 를 두 번 조회해도 같은 값이 나옵니다. 트랜잭션 도중에 다른 쪽이 커밋해서 row 값이 바뀌어도 내 트랜잭션에는 안 보입니다. RC 는 이 보장은 없습니다. 같은 트랜잭션 안에서 두 번 조회하면 그 사이에 다른 쪽이 커밋한 값이 보일 수 있습니다.

**2. row 를 만질 때 옆 자리 (gap) 도 같이 잠가 둔다.**

InnoDB 특유의 기능인데, 락을 걸 때 인덱스 위의 빈 공간 (gap) 까지 같이 잡아 둡니다. 이걸 next-key lock 이라고 부릅니다. "내가 보고 있는 범위 안에 다른 트랜잭션이 새 row 를 끼워 넣지 못하게" 막아 주는 효과입니다.

그러면 1장의 viewCount 예시에는 어떻게 적용될까요. 결론부터 말하면 **RR 의 1번 효과는 그 동시 수정을 막아 주지 않습니다.** 두 트랜잭션이 같은 row 의 viewCount=10 을 보고 각자 +1 한 값을 쓴 다음 커밋합니다. RR 도 커밋 단계에서 row 락은 잡지만, 그건 쓰는 동안만 잡는 거지 "내가 읽은 값이 그 사이에 바뀌었는지" 를 검사해 주는 락은 아닙니다.

그런데 이 프로젝트에서 그런 코드가 그동안 큰 사고 없이 굴러갔던 건, 트래픽이 모든 row 에 균등하게 분산되어 있어서 정확히 같은 row 에 정확히 같은 시점의 increment 가 부딪힐 확률이 낮았기 때문입니다. **막아 주던 건 RR 이 아니라 분산된 트래픽** 이었다는 얘기입니다.

그럼 RR 이 진짜로 막아 주던 곳은 어디냐. 예를 들어 "지난 24시간 동안 클릭이 100회를 넘은 혜택을 골라서 가장 많이 클릭된 5개에 보너스 점수를 매긴다" 같은 경우. 트랜잭션 중간에 새 클릭 row 가 끼어들면 결과가 달라지는데, gap lock 이 그 끼어듦을 막아 줍니다. 또 같은 트랜잭션 안에서 같은 row 를 두 번 읽는 코드 (1번 효과에 기대는 경우) 도 RR 이 막아 줍니다.

문제는 그 보호가 공짜가 아니라는 겁니다. **gap 까지 잡아 두니까 같은 인덱스 범위를 만지는 다른 트랜잭션이 줄을 서서 기다립니다.** 그게 처리량을 깎는 지점이었고, 격리수준을 손대 보기로 한 출발점이 됐습니다.

## 3. 왜 격리수준을 낮추기로 했나

RR 에서 RC 로 내리면 처리량이 더 나온다는 얘기는 흔히 들리는 일반론이지만, 이번에 격리수준에 손대고 싶었던 동기는 더 구체적이었습니다. 운영 중에 데드락이 한 번 났는데, 로그를 까 보니 next-key lock 끼리 서로 기다리다 풀리지 못한 게 원인이었습니다. 인덱스 범위가 살짝 겹치는 두 트랜잭션이 비슷한 시간에 들어왔는데, RR 이 양쪽에 gap lock 을 걸면서 서로의 락이 풀리길 기다리는 상황이 만들어진 거였습니다.

이걸 근본적으로 풀어 보려고 코드를 들여다보니, **실제로 RR 의 보호가 꼭 필요한 경로가 거의 없었습니다.** 대부분 쿼리는 PK 한 건 조회나 단순 UPDATE 였고, "이 트랜잭션 안에서 본 범위가 끝까지 바뀌지 않아야 한다" 가 정합성 요구사항인 코드는 손에 꼽았습니다.

그런데 그 손에 꼽는 코드들, 그러니까 동시에 같은 데이터를 만지면 안 되는 부분들이 사실 RR 이 직접적으로 막아 주던 것도 아니었습니다. viewCount 증가, 사이트 설정 토글, 사용자 설정 첫 생성 같은 곳 말입니다. 1장에서 봤듯 viewCount 의 한쪽 변경분이 사라지는 현상은 RR 이 자동으로 막아 주지 않습니다. RR 이 막아 줄 거라 (잘못) 믿고 있었을 뿐, 실제로는 트래픽이 분산된 덕분에 운 좋게 비껴 가고 있었던 셈입니다.

그래서 두 가지로 방향을 잡았습니다.

1. **격리수준은 RC 로 낮춘다.** gap lock 비용을 없애고, 그 비용에서 비롯된 데드락 가능성도 같이 줄인다.
2. **동시 수정이 일어나는 코드는 직접 식별하고 코드로 명시한다.** RR 이 막아 줄 거라 (잘못) 믿었던 부분은 RR 이 막아 주지도 않고 있었다. 이제는 진짜로 막아야 한다.

다음 장은 그래서 식별 작업입니다.

## 4. 어디가 위험한가. 네 가지 사례로 묶기

코드베이스를 훑으면서 "조회한 값을 기준으로 다시 쓰는 코드" 와 "같은 요청이 두 번 들어오면 안 되는 코드" 를 다 찾았습니다. 처음에는 흩어져 있어 보였는데, 데이터 변경의 모양으로 묶어 보니 네 가지로 정리됐습니다.

<!-- ![](/images/6/rmw_pattern_catalog.png) -->

| 사례 | 대표 케이스 | 적용한 보호 |
|---|---|---|
| 1. 카운터 증가 | `Benefit.viewCount` 증가 | 단일 SQL `UPDATE SET col = col + 1` |
| 2. 다필드 상태 전이 | `ScrapingSiteConfig` activate / disable | `@Version` 낙관락 |
| 3. 있으면 UPDATE, 없으면 INSERT | `AccountSetting` 첫 생성 | 네이티브 `INSERT ... ON DUPLICATE KEY UPDATE` |
| 4. 같은 요청이 두 번 들어와도 한 번처럼 | `ScrapingRequestedEvent` 컨슈머 | `(도메인키, 분단위 버킷)` UNIQUE + `INSERT IGNORE` |

분류를 억지로 묶은 건 아니었습니다. 데이터를 어떻게 바꾸느냐 자체가 케이스마다 다르기 때문에 자연스럽게 네 갈래로 갈렸습니다. 1번은 한 컬럼을 산술적으로 증가시키는 단순한 형태, 2번은 여러 컬럼이 한 덩어리로 바뀌는 상태 전이, 3번은 row 자체가 있을 수도 없을 수도 있는 경우, 4번은 같은 이벤트가 두 번 도착할 수 있는 경우입니다.

다음 4개 장에서 각 사례가 왜 그 보호를 골랐고, 그 보호가 정확히 어떻게 동작하는지 풀어 보겠습니다.

## 5. 사례 1. 단일 SQL UPDATE 로 한쪽 변경분이 사라지지 않게

**대표 케이스**: `Benefit.viewCount` 증가.

사용자가 혜택 상세 화면을 볼 때마다 viewCount 가 +1 됩니다. 1장에서 본 그 코드입니다.

```java
@Transactional
public void increaseViewCount(long benefitId) {
  Benefit b = benefitRepository.findById(benefitId).orElseThrow();
  b.setViewCount(b.getViewCount() + 1);
}
```

1장에서 봤듯 이 코드는 RC 에서 한쪽 변경분이 사라집니다. RR 에서도 자동으로 막히지 않습니다. 두 트랜잭션이 같은 row 의 viewCount 를 동시에 읽으면 그 뒤는 같은 값을 +1 해서 쓰는 경쟁이 됩니다.

이걸 보호하는 가장 직접적인 방법은 **조회 단계를 빼는 것** 입니다.

```java
@Modifying
@Query("UPDATE Benefit b SET b.viewCount = b.viewCount + 1 WHERE b.id = :id")
int incrementViewCount(@Param("id") long id);
```

![](/images/6/lost_update_scenario.png)

이 한 줄이 왜 동시 수정을 막느냐. DB 가 UPDATE 를 실행할 때 그 row 에 X 락을 잡고, 그 안에서 `view_count + 1` 을 계산해 씁니다. 두 트랜잭션이 같은 row 를 동시에 만지면 DB 가 두 UPDATE 를 자동으로 줄 세웁니다. 첫 UPDATE 가 락을 풀고 나가야 두 번째 UPDATE 가 들어가고, 두 번째 UPDATE 는 첫 번째가 쓴 11 을 다시 읽어서 12 로 씁니다.

여기서 짚어 둘 게 하나 있습니다. **이 보호는 격리수준 (RR / RC) 과 무관하게 동작합니다.** InnoDB 의 row 락은 어느 격리수준에서나 `UPDATE` 가 진행되는 동안 잡힙니다. RC 로 낮춰도 이 경우는 안전합니다.

이 방식의 장점은 명확합니다.

- **트랜잭션 한 단계로 끝납니다.** 조회와 변경 사이에 다른 트랜잭션이 끼어들 틈이 없습니다.
- **DB 가 이미 잘 하는 일에 위임합니다.** row 락은 InnoDB 가 격리수준과 상관없이 잘 잡습니다.
- **코드가 의도를 그대로 드러냅니다.** "이 row 의 view_count 를 +1 한다" 는 의도가 SQL 한 줄에 박혀 있어, 나중에 이 코드를 다시 봐도 동시 수정 시나리오를 한 번 더 고민할 필요가 없습니다.

여기에 낙관락이나 비관락을 굳이 얹지 않은 이유는, 그게 단일 SQL UPDATE 보다 더 비싸고 더 모호하기 때문이었습니다. 단순 카운터 증가에 낙관락을 걸면 충돌 시 재시도 정책을 따로 짜야 합니다. 비관락을 걸면 트랜잭션이 길어집니다. 그냥 +1 한 단계만 필요한 경우에는 SQL 한 줄이면 충분했습니다.

## 6. 사례 2. `@Version` 낙관락으로 상태 전이 충돌 잡기

**대표 케이스**: `ScrapingSiteConfig` 의 activate / disable.

`ScrapingSiteConfig` 는 사이트별 스크래핑 설정을 담은 엔티티입니다. "이 사이트를 지금 스크래핑 활성화한다" 같은 동작이 들어가는데, 이게 단순히 boolean 하나를 뒤집는 게 아닙니다. status, activatedAt, deactivatedAt, updatedBy 같은 컬럼이 같이 바뀌고, 그것들 사이에 정합성 규칙도 있습니다. status 가 ACTIVE 인데 activatedAt 이 null 이면 안 된다는 식입니다.

여기에 단일 SQL UPDATE 를 쓰는 건 어색합니다. 여러 컬럼을 한 SQL 로 묶을 수는 있지만, SQL 문자열 안에 비즈니스 규칙이 들어가 버립니다. 그리고 여기는 사용자 트래픽이 무더기로 같은 row 를 동시에 만지는 케이스가 아닙니다. 두 운영자가 거의 동시에 같은 사이트 설정을 만지는 경우입니다. 자주 일어나는 충돌이 아니라, **일어나면 명시적으로 알려야 하는 충돌** 입니다.

그래서 여기에는 `@Version` 낙관락을 걸어 두기로 했습니다.

```java
@Entity
public class ScrapingSiteConfig {
  @Id
  Long id;

  @Version
  Long version;

  // status, activatedAt, ...
}
```

JPA 가 자동으로 해 주는 일은 이렇습니다. 엔티티가 수정되어 flush 될 때 UPDATE 쿼리에 `WHERE id = ? AND version = ?` 조건이 들어갑니다. 그리고 SET 절에 `version = version + 1` 도 같이 들어갑니다.

두 운영자가 동시에 같은 config 를 만지면 어떻게 되는지 보겠습니다.

- T1: 조회. version = 5, 모든 필드 들고 옴
- T2: 조회. version = 5, 모든 필드 들고 옴
- T1: `activate()` → `UPDATE ... SET status='ACTIVE', version=6 WHERE id=? AND version=5` → 1 row 영향
- T2: `disable()` → `UPDATE ... SET status='DISABLED', version=6 WHERE id=? AND version=5` → 0 row 영향

T2 의 UPDATE 는 0 row 영향입니다. 이미 version 이 6 으로 올라가 있어서 WHERE 절이 안 맞기 때문입니다. JPA 는 이걸 감지하고 `OptimisticLockingFailureException` 을 던집니다. 핵심은 **충돌이 일어났다는 사실이 사라지지 않고 위로 올라온다** 는 점입니다.

이걸 어디서 잡느냐는 정책의 문제입니다. 이 프로젝트는 두 갈래로 나눠 뒀습니다.

- **자동 파이프라인이 충돌한 경우**: service 안에서 짧게 재시도. 다시 조회해서 최신 version 으로 한 번 더 시도하고, 그래도 충돌하면 위로 던집니다. 자동 파이프라인은 동일 작업을 반복해도 무방한 경우가 많아 이게 가능합니다.
- **운영자가 UI 에서 충돌한 경우**: 재시도하지 않습니다. "다른 운영자가 동시에 같은 설정을 변경했습니다. 화면을 새로고침하고 다시 시도해 주세요" 같은 친화적 에러로 응답합니다. 누구의 변경이 묻혔는지를 운영자에게 알려 줘야 하기 때문입니다.

이런 상황에서 한쪽 변경분이 통째로 사라지면 그건 곧 운영 사고가 됩니다. 한 운영자는 활성화했다고 알고 있는데 실제로는 비활성화 상태로 남아 있는 식이니까요. `@Version` 은 그 사고를 막아 줍니다.

### 무중단 배포와의 호환

`@Version` 컬럼을 추가하는 Flyway 마이그레이션은 이렇게 갑니다.

```sql
ALTER TABLE scraping_site_config
  ADD COLUMN version BIGINT NOT NULL DEFAULT 0;
```

`DEFAULT 0` 이 있으니, 이전 버전 어플리케이션이 version 컬럼을 모른 채 UPDATE 해도 (즉 SET 절에 version 이 들어가지 않아도) DB 가 알아서 0 으로 두고 넘어갑니다. 무중단 배포 중에 신구 버전이 같은 DB 를 동시에 쓰는 수 초~수십 초 동안에도 양쪽 다 정상 동작합니다. 한쪽이 깨지지 않습니다. 무중단 배포에서 컬럼 추가/제거를 안전하게 가져가는 핵심 패턴이 이겁니다.

## 7. 사례 3. 있으면 UPDATE, 없으면 INSERT 가 의외로 어려웠던 이야기

**대표 케이스**: `AccountSetting`.

`AccountSetting` 은 사용자 한 명당 row 한 개씩 들어가는 알림 설정 엔티티입니다. 사용자가 처음 알림 설정 화면에 들어왔을 때 row 가 없으면 만들고, 두 번째부터는 업데이트합니다.

가장 직관적인 코드는 이렇게 생겼습니다.

```java
@Transactional
public void updateSetting(long accountId, AccountSettingDto dto) {
  AccountSetting setting = settingRepository.findByAccountId(accountId)
      .orElseGet(() -> new AccountSetting(accountId));
  setting.applyFrom(dto);
  settingRepository.save(setting);
}
```

이게 RC 에서 왜 위험한지는 두 클라이언트가 같은 사용자의 첫 알림 설정 화면에 거의 동시에 들어왔을 때 드러납니다.

- T1: `findByAccountId` → 없음 → `new AccountSetting(accountId)`
- T2: `findByAccountId` → 없음 → `new AccountSetting(accountId)`
- T1: `setting.applyFrom(dto1)` → `save` → INSERT 성공
- T2: `setting.applyFrom(dto2)` → `save` → INSERT (UNIQUE 제약 충돌)

`account_id` 에 UNIQUE 제약이 걸려 있다면 T2 의 INSERT 가 `DataIntegrityViolationException` 으로 터집니다. UNIQUE 제약이 없다면 둘 다 INSERT 되어 같은 사용자의 설정 row 가 두 개 생기는 더 나쁜 사고가 납니다.

처음에 떠올린 대응은 service 메서드 안에서 그 예외를 catch 해서 다시 시도하는 것이었습니다. 그런데 이게 의외로 안 됐습니다. Hibernate 가 깊은 곳에서 발목을 잡았습니다. 시도해 본 것들과 그게 왜 실패했는지를 순서대로 풀어 보겠습니다.

### 시도 1. 메서드 안에서 `saveAndFlush` + try-catch

```java
try {
  settingRepository.saveAndFlush(setting);
} catch (DataIntegrityViolationException e) {
  // 다시 조회해서 update 로 가자
  setting = settingRepository.findByAccountId(accountId).orElseThrow();
  setting.applyFrom(dto);
}
```

이렇게는 안 됩니다. Hibernate 의 동작 방식 때문입니다. `saveAndFlush` 가 INSERT 를 시도하다가 DB 가 무결성 위반을 던지면, 그 시점에 Hibernate 의 영속성 컨텍스트가 깨진 상태로 빠집니다. 같은 트랜잭션 안에서 그 뒤에 무슨 JPA 작업을 걸어도 `AssertionFailure: null identifier` 같은 형태로 다시 터집니다. 이미 깨진 영속성 컨텍스트는 catch 해서 회복시킬 수 없습니다.

`@Transactional(noRollbackFor = ...)` 도 같은 한계가 있습니다. 이건 Spring 의 트랜잭션 롤백 마킹을 막아 줄 뿐, Hibernate 세션 자체가 깨지는 걸 막아 주지는 않습니다.

### 시도 2. service 안에서 `TransactionTemplate` 로 트랜잭션 쪼개기

각 시도를 별도 트랜잭션에 넣고, 첫 시도가 실패하면 두 번째 트랜잭션에서 UPDATE 로 가자는 발상입니다. 동작은 합니다. 그런데 service 로직이 트랜잭션 경계 관리 코드로 비대해집니다. 5줄짜리 service 가 30줄로 늘어납니다. service 가 떠안지 말아야 할 책임을 떠안고 있다는 신호이기도 합니다.

### 시도 3. `REQUIRES_NEW` 를 adapter 쪽에 두기

비슷한 발상을 어노테이션으로 푸는 방법인데, 이 프로젝트의 레이어링 규칙상 `@Transactional` 은 service 레이어에만 둡니다. adapter (persistence 레이어) 에 트랜잭션 경계가 들어가면, 트랜잭션이 어디서 시작하고 어디서 끝나는지 service 만 봐서는 알 수 없게 됩니다. 디버깅이 까다로워지고, 나중에 PR 을 다시 봐도 트랜잭션 경계가 한눈에 안 보입니다.

### 시도 4. DB 에 위임. `INSERT ... ON DUPLICATE KEY UPDATE`

결국 답은 DB 가 이미 잘 하는 일에 위임하는 것이었습니다. MySQL 은 `INSERT ... ON DUPLICATE KEY UPDATE` 라는 구문을 제공합니다. UNIQUE 제약이 걸린 row 가 이미 있으면 INSERT 가 아니라 UPDATE 로 분기합니다. 이 분기 자체가 DB 안에서 row 락 하나로 끝나기 때문에, 두 클라이언트가 동시에 와도 한쪽이 INSERT, 다른 쪽이 UPDATE 로 자동으로 정리됩니다.

```java
@Modifying
@Query(value = """
    INSERT INTO account_setting
      (account_id, notification_enabled, ...)
    VALUES
      (:accountId, :enabled, ...)
    ON DUPLICATE KEY UPDATE
      notification_enabled = VALUES(notification_enabled),
      ...
    """, nativeQuery = true)
int upsertSetting(@Param("accountId") long accountId,
                  @Param("enabled") boolean enabled,
                  ...);
```

service 는 이 한 줄을 호출하면 끝입니다. Hibernate 영속성 컨텍스트와 무관하게 SQL 한 방으로 분기가 끝나니까, 앞의 세 시도가 빠졌던 함정에서 자유롭습니다.

이 케이스에서 배운 점을 정리하면 이렇습니다. **있으면 UPDATE, 없으면 INSERT 같은 경우는 어플리케이션 코드에서 조회-분기-쓰기로 구현하는 순간 한쪽 변경분이 사라지거나 UNIQUE 제약으로 터질 가능성이 생깁니다.** 도메인에서 정합성을 어디까지 요구하느냐에 따라 답은 달라지겠지만, 적어도 내 경우 "한 사용자에 row 하나" 같은 강한 UNIQUE 가 깔린 케이스에서는 DB 의 원자적 분기 구문에 위임하는 게 가장 깔끔했습니다. 어플리케이션 안에서 try-catch 로 풀려고 시도해 본 만큼, 그 비용을 한 번 치러 본 결론이기도 합니다.

### 부수 학습. H2 와의 호환

이 방식에는 단점도 하나 있습니다. H2 데이터베이스는 `INSERT ... ON DUPLICATE KEY UPDATE` 문법을 지원하지 않습니다. H2 의 `MERGE INTO` 와는 문법이 다르기 때문에, 슬라이스 테스트 (H2 인메모리) 로 이 부분을 검증할 수 없습니다. 통합 테스트 (Testcontainers MySQL) 로 옮겨야 합니다.

테스트 실행이 느려지는 비용이 있지만, 동시성 보호를 위해 감수했습니다. 슬라이스 테스트로 검증되지 않는 SQL 한 줄을 두는 대신, 그 SQL 한 줄이 막아 주는 동시 수정 시나리오가 더 크다고 봤습니다.

## 8. 사례 4. 같은 요청이 두 번 들어와도 한 번처럼

**대표 케이스**: `ScrapingRequestedEvent` 컨슈머.

이 프로젝트는 모듈 간 비동기 통신에 Spring Modulith 의 이벤트 시스템을 씁니다. 한 모듈이 이벤트를 발행하면, 그걸 구독하는 다른 모듈의 컨슈머가 받아서 처리합니다.

Spring Modulith 가 보장해 주는 한 가지는 **이벤트가 최소 한 번은 컨슈머까지 도달한다** 는 점입니다. 다르게 말하면 **같은 이벤트가 한 번 더 도달할 수도 있다** 는 뜻이기도 합니다. 컨슈머가 처리 도중에 어플리케이션이 죽으면 재시작 후 다시 보냅니다.

그러면 컨슈머 쪽 코드는 "같은 이벤트가 두 번 들어와도 결과가 한 번 들어왔을 때와 같아야 한다" 는 요구사항을 떠안게 됩니다. 이걸 멱등성이라고 부릅니다. 풀어 쓰면 **같은 요청이 두 번 들어와도 한 번처럼 끝나야 한다** 는 뜻입니다.

`ScrapingRequestedEvent` 는 "이 사이트의 최신 정보를 지금 가져와라" 라는 이벤트입니다. 이 프로젝트는 외부 사이트 페이지를 서버에서 프로그램으로 띄운 브라우저(헤드리스 브라우저) 로 열어 본문을 읽어 오는 방식으로 정보를 수집하는데, 이 작업을 흔히 스크래핑이라고 부릅니다. 컨슈머는 이 이벤트를 받아 그 무거운 외부 호출을 실제로 수행합니다. 한 번이면 좋은데, 두 번 들어오면 대상 사이트에 두 번 부담을 주고 (그쪽 입장에서 좋아 보일 리가 없습니다), 어플리케이션 쪽도 같은 비싼 작업을 두 번 합니다.

### 해결책. 멱등키 테이블

컨슈머가 작업을 시작하기 전에, 별도 테이블에 자기 식별자를 먼저 기록해 봅니다. 기록에 성공하면 "내가 첫 호출자다" 라는 뜻이니 작업을 진행하고, 실패하면 (이미 다른 호출자가 같은 키를 기록해 둠) 그대로 빠져나옵니다.

```sql
CREATE TABLE scraping_request_consumer_idempotency (
  id            BIGINT      NOT NULL AUTO_INCREMENT PRIMARY KEY,
  site_id       BIGINT      NOT NULL,
  minute_bucket BIGINT      NOT NULL,
  created_at    DATETIME(6) NOT NULL,
  UNIQUE KEY uk_site_minute (site_id, minute_bucket)
);
```

```java
@EventListener
@Transactional
public void onScrapingRequested(ScrapingRequestedEvent event) {
  long minuteBucket = event.requestedAt().getEpochSecond() / 60;
  int affected = idempotencyRepository.tryReserve(event.siteId(), minuteBucket);
  if (affected == 0) {
    // 같은 (사이트, 분) 조합이 이미 기록되어 있다. 빠져나감
    return;
  }
  // 첫 호출자다. 실제 작업 진행
  scrapingService.run(event.siteId());
}
```

`tryReserve` 는 `INSERT IGNORE INTO ...` 한 줄짜리 네이티브 쿼리입니다. UNIQUE 제약 충돌이 나면 그냥 무시하고 영향 row 가 0 으로 반환됩니다. 새로 기록되면 1.

![](/images/6/minute_bucket_idempotency.png)

핵심은 키를 **`(site_id, minute_bucket)`** 으로 잡았다는 점입니다.

### 왜 분단위 버킷이냐

더 엄격한 방식은 이벤트마다 UUID 를 발급해서 그 UUID 단위로 중복을 거르는 것입니다. 두 가지 이유로 그 길로 가지 않았습니다.

**1. 뒷단이 이미 자체 UNIQUE 로 받쳐 줍니다.**

스크래핑으로 가져온 원본은 `(출처, 원본 식별자)` UNIQUE, 거기서 추출한 결과물은 시도 번호 UNIQUE, 최종 후보는 별도 후보 식별자 UNIQUE 가 걸려 있습니다. 같은 이벤트가 1분 구간을 넘어 또 들어와도, 뒷단의 데이터 레이어가 한 번 더 흡수해 줍니다. 즉 이 멱등키 테이블이 책임질 일은 **비용이 큰 외부 호출 (헤드리스 브라우저로 외부 사이트 열기) 을 두 번 안 한다** 는 보호 한 가지뿐입니다. 데이터 정합성은 뒷단이 잡습니다.

**2. UUID 단위 중복 거르기는 비용이 큽니다.**

모든 이벤트 payload 에 UUID 필드를 강제로 넣어야 하고, 중복 거르기 테이블이 무기한 자랍니다 (혹은 보관 기간 정책을 따로 짜야 함). 분단위 버킷은 "최근 1시간만 보관" 같은 정리 정책으로 가볍게 스스로 정리됩니다. 같은 사이트에 1분 안에 두 번 요청이 들어오는 건 비정상이고, 1분이 지난 뒤에 또 들어오면 그건 정상 새 요청으로 처리해도 비즈니스 관점에서 문제가 없습니다.

### "정확히 한 번" 은 아닙니다

1분 구간을 넘어 같은 이벤트가 또 들어오면 이 멱등키는 다시 통과시킵니다. 실제로는 **컨슈머 쪽 분단위 요청 제한 + 짧은 시간 안에 중복으로 들어온 이벤트 흡수** 에 가깝고, 그 너머의 정합성은 뒷단의 UNIQUE 제약이 잡습니다. 두 레이어가 합쳐져서 시스템이 견디는 구조입니다.

## 9. 격리수준을 실제로 낮추기

위 네 가지 사례에서 코드를 다 보강하고 나서야 RR → RC 전환을 실행했습니다. 순서가 중요합니다. **코드 보강이 먼저, 격리수준 변경이 그 다음.** 반대로 가면 RR 이 (운 좋게) 막아 주던 동시 수정이 RC 에서 그대로 터집니다.

전환은 두 곳의 설정만 바꾸면 됩니다.

**1. 운영 DB 의 격리수준 파라미터** 를 READ-COMMITTED 로. 최신 MySQL 에서 이 파라미터는 동적으로 적용되어 재부팅이 필요 없습니다. 인프라 설정 한 줄을 바꿔서 배포하면 즉시 RC 로 전환됩니다.

**2. 어플리케이션의 datasource 설정** 에서 HikariCP 의 `transaction-isolation` 을 `TRANSACTION_READ_COMMITTED` 로 명시합니다. 읽기 풀과 쓰기 풀을 분리해 두고 있다면 양쪽 다 똑같이 둡니다.

코드 레벨에서는 변경이 없습니다. `@Transactional(isolation = ...)` 을 일일이 바꿀 일도 없습니다. 두 곳의 설정 한 줄씩만 바뀌면 모든 트랜잭션의 기본 격리수준이 RC 로 바뀝니다.

### 무중단 배포 중의 정합성

무중단 배포가 진행되는 동안에는 한쪽 인스턴스가 RR, 다른 한쪽이 RC 로 같이 도는 수 초~수십 초의 시간이 있습니다. 그 시간에도 정합성이 깨지지 않게 보장해 주는 게 네 가지 사례 보강이었습니다. 단일 SQL UPDATE 도, `@Version` 낙관락도, 네이티브 `ON DUPLICATE KEY UPDATE` 도, 멱등키 INSERT IGNORE 도, 어느 격리수준에서나 똑같이 동작합니다. 그 시간은 곧 끝나고, 다음부터는 모두 RC 입니다.

순서를 한 번 더 정리하면 이렇습니다.

1. 네 가지 사례 보강을 한 PR 로 묶어서 머지.
2. 운영 DB 의 격리수준 파라미터 변경 (DB 가 즉시 RC 로 전환).
3. 무중단 배포로 새 어플리케이션 인스턴스 띄우기 (이 시점에 datasource 의 RC 가 적용).
4. 일정 시간 모니터링.

배포 직후 RR 의 gap lock 에서 비롯되던 데드락 패턴이 사라졌습니다.

## 10. 회고. 무엇이 남고 무엇을 양보했나

이번 작업에서 내린 결정은 결국 두 가지였습니다. 하나는 격리수준을 한 단계 낮추기로 한 결정, 다른 하나는 그러면서 잃은 보호를 어플리케이션 코드로 끌어올리기로 한 결정입니다.

**얻은 것**

- **처리량**. RR 의 gap lock 비용이 사라지고, 그 비용에서 비롯된 데드락 패턴도 사라졌습니다.
- **코드가 의도를 드러내게 된 것**. 각 케이스에 명시적으로 보호를 걸어 두니, 나중에 코드를 다시 봐도 "이 부분에 동시 수정이 들어오면 어떻게 되는가" 라는 질문에 코드만 보고도 답이 나옵니다. 이전에는 그 답이 "RR 이 막아 줄 거예요" 였는데, 사실 정확한 답이 아니었습니다.

**양보한 것**

- **트랜잭션 안에서 본 데이터가 끝까지 그대로 보이는 보장**. RR 이 주던 이 보장이 RC 에서는 약해집니다. 같은 트랜잭션 안에서 같은 row 를 두 번 조회하면 다른 값이 나올 수도 있습니다. 다만 이 보장에 기대는 코드는 거의 없었고, 있더라도 비관락 (`SELECT ... FOR UPDATE`) 이나 명시적 스냅샷 패턴으로 다시 잡으면 됩니다.
- **읽기 리플리카를 쓸 때 마스터로 고정해야 하는 트랜잭션 구간**. RC 에서 읽기 리플리카로 흘러가는 조회는 약간의 시점 차이를 보일 수 있습니다. 트랜잭션 안에서 같은 row 를 두 번 읽어야 하는 코드는 리플리카가 아니라 마스터로 고정해야 합니다. 이건 읽기/쓰기 분리를 본격적으로 적용하는 시점에 다시 보기로 하고 지금은 미뤄 뒀습니다.

마지막으로 처음에 던진 질문, "하나의 작업이 원자적으로 끝나는 경계를 어디에 둘 것인가" 로 돌아가 보겠습니다. 막상 코드를 한 바퀴 돌아 보니, 케이스마다 답이 다 달랐습니다.

- 카운터 증가의 경계는 **단일 SQL 한 줄**.
- 상태 전이의 경계는 **`@Version` 한 컬럼**.
- 있으면 UPDATE, 없으면 INSERT 의 경계는 **DB 의 `ON DUPLICATE KEY UPDATE` 구문**.
- 같은 이벤트가 두 번 들어오는 경우의 경계는 **분단위 멱등 테이블**.

데이터 변경의 모양이 케이스마다 다르고, 그 모양에 맞는 보호도 다르기 때문에 답이 갈리는 것이었습니다.

> **DB 격리수준은 정합성 정책의 기본값일 뿐이다. 정합성을 끝까지 책임지는 건 결국 어플리케이션 코드라는 것을 이 작업을 거치며 다시 느꼈다.**

이 문장을 손에 들고 코드를 한 바퀴 돌아보니, "이 부분은 안전한가, 안전하지 않다면 어떤 보호가 맞는가" 라는 질문에 하나씩 답을 달 수 있게 됐습니다. 그렇게 답을 채워 가는 일이 사실 백엔드 개발자가 가장 자주 하는 일 중 하나라는 걸 이번 작업으로 다시 느꼈습니다.
