## 들어가며

Java Virtual Thread가 하는 일은 결국 하나입니다. 개발자는 blocking API를 그대로 쓰는데, 내부에서는 그걸 non-blocking으로 바꿔 Carrier Thread(가상 스레드를 실제로 싣고 도는 OS 스레드)를 놀리지 않는 것입니다. 이 글은 그게 JVM 수준에서 어떻게 가능한지, 그리고 M:N 스레딩 모델에서 생기는 동기화 문제를 어떻게 풀었는지를 다룹니다. 구체적으로는 다음 두 가지입니다.

- **Blocking I/O 시 Virtual Thread만 분리되고 OS 스레드는 다른 일을 하는 메커니즘**: `Socket.read()`, `Thread.sleep()` 같은 blocking API를 호출했을 때 JVM이 내부적으로 어떻게 OS의 non-blocking I/O(Linux의 `epoll`)를 쓰는가
- **M:N 스레딩 모델에서의 동기화**: ForkJoinPool의 work-stealing 스케줄러, 그리고 JDK 21~23 시절의 pinning이 JEP 491(JDK 24)에서 어떻게 해결됐는가

> Virtual Thread의 바탕이 되는 사용자 수준 스레드(Green Thread) 자체가 어떻게 동작하는지(컨텍스트 스위칭, 스택 관리, 협력형 스케줄링)를 C 언어로 바이트 단위까지 파헤친 [가상 스레드는 어떻게 동작하는가 - C로 직접 구현해 보기]({{< ref "2.md" >}}) 글도 있습니다. 앞 글에서 그 사용자 수준 스레드를 C로 직접 구현해 본 뒤, 이 글은 그 위에 올려진 JVM 층을 JEP와 JDK 동작을 따라가며 정리한 것입니다.

## 1. Blocking API 뒤에서 일어나는 일

### 1-1. 개발자가 보는 코드

Virtual Thread에서 네트워크 I/O를 수행하는 코드는 기존과 완전히 동일합니다.

```java
Thread.ofVirtual().start(() -> {
    try (var socket = new Socket("example.com", 80)) {
        InputStream in = socket.getInputStream();
        byte[] buf = new byte[1024];
        int n = in.read(buf);  // 여기서 블로킹... 하는 것처럼 보임
        System.out.println("Read " + n + " bytes");
    } catch (IOException e) {
        e.printStackTrace();
    }
});
```

`in.read(buf)`는 데이터가 도착할 때까지 현재 스레드를 **블로킹**합니다. Platform Thread였다면 OS 스레드가 sleep 상태에 빠져 아무 일도 하지 못합니다.

하지만 Virtual Thread에서는 이야기가 완전히 다릅니다.

### 1-2. JVM 내부에서 벌어지는 일

Virtual Thread가 `Socket.read()` 같은 Blocking API를 호출하면, JVM 내부에서는 다음과 같은 일이 순차적으로 발생합니다.

![](/images/3/io_flow.png)

핵심은 **(1)번**입니다. **JVM이 개발자 모르게 소켓을 non-blocking 모드로 바꿉니다.** 개발자는 blocking API를 호출했지만, OS 수준에서는 non-blocking I/O가 수행되는 것입니다.

### 1-3. Continuation.yield() - Virtual Thread의 핵심

`Continuation.yield()`는 사용자 수준 스레드의 "실행 중단 후 재개" 동작을 JVM 수준에서 구현한 것입니다. 일반적인 Green Thread에서는 callee-saved 레지스터를 스택에 저장하고 다른 스레드의 스택 포인터로 점프하는 식으로 처리하지만, JVM에서는 스택 프레임 자체를 힙으로 옮기는 방식을 씁니다.

![](/images/3/continuation_yield.png)

C 구현과의 결정적인 차이가 있습니다. C에서는 스택을 `malloc`으로 할당한 고정 메모리에 유지했지만, Java의 `Continuation`은 **스택 프레임을 힙으로 복사** 합니다.

| 동작 | C Green Thread | Java Virtual Thread |
|------|----------------|---------------------|
| yield 시 | 스택 포인터만 전환 | 스택 프레임을 힙으로 복사 (unmount) |
| resume 시 | 저장된 스택 포인터로 복귀 | 힙에서 스택 프레임 복원 (mount) |
| 스택 크기 | 고정 (64KB 등) | 동적 (사용한 만큼만) |
| 메모리 효율 | 사전 할당 필요 | 실제 사용량에 비례 |

이 "스택 프레임의 힙 복사"가 가능한 이유는 JVM이 바이트코드 수준에서 스택 프레임의 구조를 완전히 파악하고 있기 때문입니다. C에서는 CPU 레지스터를 직접 조작해야 했던 것과는 근본적으로 추상화 수준이 다릅니다.

## 2. OS Non-blocking I/O와의 연결

### 2-1. 핵심 - blocking되는 주체가 바뀐다

전통적인 Blocking I/O에서는 **OS 스레드**가 블로킹됩니다.

![](/images/3/platform_blocking.png)

Virtual Thread에서는 **Virtual Thread만** 블로킹되고, OS 스레드(Carrier Thread)는 즉시 다른 일을 합니다.

![](/images/3/vthread_nonblocking.png)

이게 Virtual Thread의 핵심입니다. 개발자는 Blocking API를 그대로 쓰는데, OS 수준에서는 non-blocking I/O가 돌아서 Carrier Thread를 낭비하지 않습니다.

### 2-2. Poller - I/O 완료를 감지하는 감시자

Virtual Thread가 yield된 후, 누군가는 "I/O가 완료되었는지"를 감시해야 합니다. 이 역할을 하는 것이 JVM 내부의 **Poller** 스레드입니다.

Poller는 OS가 제공하는 I/O 이벤트 알림 메커니즘을 사용합니다. 이 글은 Linux를 기준으로 하고, Linux에서 JDK Poller는 **`epoll`** 을 씁니다.

| 메커니즘 | 특징 |
|---|---|
| `epoll` (Linux) | 이벤트 기반(readiness-based) 알림, fd가 읽기/쓰기 가능해지면 통지. 대부분의 Java 서버 환경 |

JDK 내부에서 이 Poller의 동작을 간략히 표현하면 다음과 같습니다.

```
[Poller 스레드 - JVM 내부 데몬 스레드]

while (true) {
    // OS의 I/O 이벤트 대기 (Linux 기준)
    events = epoll_wait(epollFd, ...);

    for (event : events) {
        // 이벤트가 발생한 fd에 대응하는 Virtual Thread를 찾음
        VirtualThread vt = fdToVirtualThread.get(event.fd);

        // 해당 Virtual Thread를 ForkJoinPool에 다시 제출
        vt.unpark();  // → ForkJoinPool의 작업 큐에 추가됨
    }
}
```

### 2-3. 전체 흐름 정리 - Socket.read() 한 번의 처리 과정

하나의 `Socket.read()` 호출이 Virtual Thread 내부에서 완료되기까지의 전체 흐름을 정리하면 다음과 같습니다.

![](/images/3/socket_read_timeline.png)

이 과정에서 **Carrier Thread는 단 한 순간도 블로킹되지 않습니다.** VT-1이 I/O를 기다리는 동안 VT-2의 작업을 처리하고, I/O가 완료되면 다시 VT-1을 이어서 실행합니다.

### 2-4. Thread.sleep()도 마찬가지

네트워크 I/O뿐 아니라 `Thread.sleep()`도 동일한 메커니즘으로 동작합니다.

```java
Thread.ofVirtual().start(() -> {
    System.out.println("작업 시작");
    Thread.sleep(Duration.ofSeconds(5));  // Carrier Thread를 블로킹하지 않음
    System.out.println("5초 후 재개");
});
```

Virtual Thread에서 `Thread.sleep()`을 호출하면 다음과 같은 일이 벌어집니다.

1. JVM이 내부적으로 타이머를 등록합니다 (스케줄링된 작업).
2. `Continuation.yield()`로 Virtual Thread를 unmount합니다.
3. Carrier Thread는 즉시 해방되어 다른 Virtual Thread를 실행합니다.
4. 지정된 시간이 지나면 타이머가 만료되고, 해당 Virtual Thread를 다시 스케줄링합니다.

Platform Thread에서의 `Thread.sleep(5000)`은 OS 스레드를 5초간 완전히 점유하지만, Virtual Thread에서는 Carrier Thread를 1ms도 낭비하지 않습니다.

## 3. M:N 스레딩 모델과 ForkJoinPool

### 3-1. M:N 모델이란

Virtual Thread는 **M:N 스레딩 모델**을 사용합니다. M개의 Virtual Thread가 N개의 Carrier Thread(OS Thread) 위에서 다중화(multiplexing)되는 구조입니다.

![](/images/3/mn_model.png)

| 스레딩 모델 | 예시 | 특징 |
|---|---|---|
| 1:1 | Java Platform Thread | Virtual Thread 1개 = OS Thread 1개 |
| M:1 | 초기 Green Thread (Java 1.1) | 모든 Green Thread가 OS Thread 1개 위에서 실행 |
| M:N | Java Virtual Thread | M개의 VT가 N개의 OS Thread에 다중화 |

M:1 모델은 멀티코어를 못 쓴다는 결정적 한계가 있었습니다. M:N 모델은 이 문제를 해결하면서도 스레드 생성 비용을 낮게 유지합니다.

### 3-2. ForkJoinPool - Virtual Thread의 스케줄러

Virtual Thread의 Carrier Thread 풀은 `ForkJoinPool`입니다. 기본 설정은 다음과 같습니다.

| 설정 | 기본값 | 시스템 프로퍼티 |
|---|---|---|
| 스레드 수 | `Runtime.availableProcessors()` | `jdk.virtualThreadScheduler.parallelism` |
| 최대 스레드 수 | 256 | `jdk.virtualThreadScheduler.maxPoolSize` |
| 스케줄링 방식 | 자기 큐 FIFO (async 모드, 기본) | (공개 프로퍼티 아님) |

이 ForkJoinPool은 애플리케이션이 `ForkJoinPool.commonPool()`로 사용하는 것과는 별도의 인스턴스입니다. Virtual Thread 전용으로 JVM 내부에서 관리됩니다.

### 3-3. Work-Stealing 알고리즘

ForkJoinPool이 일반적인 ThreadPoolExecutor와 다른 점은 **work-stealing** 알고리즘입니다.

![](/images/3/work_stealing.png)

각 Worker Thread(Carrier Thread)가 자신만의 작업 큐(deque)를 가지고 있습니다.

- Virtual Thread 전용 스케줄러는 각 워커가 **자신의 큐를 FIFO로** 처리합니다. async 모드가 기본이라 먼저 제출된 Virtual Thread가 먼저 실행되어 공평성이 유지됩니다.
- 자신의 큐가 비면, 다른 Worker의 큐 **반대편**에서 작업을 **steal**합니다.
- (참고) 분할정복 연산에 쓰는 일반 `ForkJoinPool`은 반대로 자신의 큐를 **LIFO**(스택처럼)로 꺼내 캐시 지역성을 살립니다. 이는 Virtual Thread 스케줄러의 기본 동작과 다릅니다.

이 구조 덕분에 공유 큐에 대한 lock contention이 최소화되고, 모든 Carrier Thread가 균등하게 바쁘게 유지됩니다. Virtual Thread가 수십만 개여도 스케줄링 오버헤드가 낮은 이유가 여기에 있습니다.

## 4. Pinning - JEP 491 전과 후

Virtual Thread의 전제는 Blocking I/O 시 Carrier Thread에서 **unmount**되는 것이지만, 특정 조건에서는 unmount가 막혀 Virtual Thread가 Carrier Thread에 **고정(pin)** 되는 현상이 있었습니다. 이것이 **Pinning** 입니다.

### 4-1. JDK 21~23에서의 Pinning

이 시기의 pinning 원인은 두 가지였습니다.

| 원인 | 설명 |
|---|---|
| `synchronized` 블록/메서드 내부에서 블로킹 | JVM 모니터(monitor)를 잡은 상태에서는 스택 프레임을 힙으로 복사할 수 없음 |
| 네이티브(JNI) 메서드 실행 중 | 네이티브 스택 프레임은 JVM이 관리할 수 없음 |

두 원인 중 현장에서 더 큰 타격을 준 쪽은 **`synchronized` 안의 블로킹 I/O**였습니다. 대표적인 예가 JDBC 드라이버입니다. 많은 드라이버가 내부에서 `synchronized` 블록을 잡은 채 DB 네트워크 I/O를 수행했고, 요청 경로에 JDBC가 끼는 순간 Carrier Thread가 DB 응답을 기다리며 통째로 묶였습니다. 당시 권장 회피책은 `synchronized`를 `ReentrantLock`으로 교체하는 것이었습니다. 하지만 이건 어디까지나 사용자가 직접 쓴 코드 한정이고, 외부 라이브러리 내부의 `synchronized`는 우리가 손댈 수 없었습니다.

### 4-2. JEP 491(JDK 24)이 해결한 것

JDK 24의 [JEP 491 — Synchronize Virtual Threads without Pinning](https://openjdk.org/jeps/491)이 이 문제를 근본적으로 해결했습니다. `synchronized` 블록 안에서도 Virtual Thread가 정상적으로 unmount되고, `Object.wait()`도 Carrier를 잡지 않습니다. JEP 491 이후 남아 있는 pinning 원인은 **네이티브(JNI) 메서드 실행 중** 하나뿐입니다.

| 조건 | JDK 21~23 | JDK 24+ (JEP 491) |
|---|---|---|
| `synchronized` 안의 블로킹 I/O | Pinning 발생 | 정상 unmount |
| `Object.wait()` | Carrier 점유 | Carrier 해방 |
| 네이티브(JNI) 메서드 실행 중 | Pinning 발생 | **여전히 Pinning** |

정리하면, JDK 24+를 전제로 한다면 `synchronized`를 `ReentrantLock`으로 교체하는 작업은 **더 이상 기본 권장사항이 아닙니다.** 기존 라이브러리를 JDK 24+ 위에서 돌리는 것만으로 JDBC 드라이버 같은 곳의 pinning이 대부분 자연히 사라지고, pinning 회피용 플랫폼 스레드 풀을 따로 만들 실용적 이유도 대부분 없어집니다.

### 4-3. 감지 방법

JDK 21~23에서는 `-Djdk.tracePinnedThreads=full`로 pinning 스택 트레이스를 출력할 수 있었습니다. JDK 24+에서는 JFR 이벤트로 통합되어 `jfr print`나 JMC로 확인합니다. 네이티브 경로에서 남은 pinning이 있는지 의심될 때는 JFR 쪽을 먼저 봅니다.

## 5. ScopedValue - 컨텍스트 전파 원시 타입

JEP 491 이후에도 Virtual Thread와 함께 재검토가 필요한 한 가지가 남습니다. 바로 **컨텍스트 전파**입니다.

`ThreadLocal`은 Platform Thread 환경에서는 크게 문제되지 않았습니다. 스레드 풀의 크기가 제한적이었기 때문에 살아 있는 `ThreadLocalMap` 수도 자연히 제한됐기 때문입니다. 하지만 Virtual Thread는 요청마다 새로 만들어지고 수십만 개까지 동시 생존할 수 있어, `set()`이 한 번이라도 호출된 Virtual Thread만큼 Map이 함께 살아남습니다. 게다가 `set()`과 `remove()`를 짝 맞춰 부르는 걸 개발자가 직접 챙겨야 해서, 예외 경로에서 `remove()`를 빠뜨리기 쉽습니다.

Java 25에서 정식 기능이 된 **`ScopedValue`** 는 이 두 문제를 동시에 걷어냅니다.

- 값이 불변(immutable)이고 블록 스코프가 끝나면 자동 해제되므로 `remove()` 누락 자체가 불가능
- 값의 수명이 스코프 단위라 Virtual Thread 수명 전체에 Map을 들고 있을 이유가 없음

```java
private static final ScopedValue<String> REQUEST_ID = ScopedValue.newInstance();

public void handleRequest(String requestId) {
    ScopedValue.where(REQUEST_ID, requestId).run(() -> {
        // 이 블록 안에서만 REQUEST_ID.get() 으로 값 접근 가능
        processStep1();
        processStep2();
    });
    // 블록을 벗어나는 순간 바인딩 자동 해제
}
```

| 비교 | `ThreadLocal` | `ScopedValue` |
|---|---|---|
| 생명주기 | 스레드 수명 전체 | 블록 스코프 한정 |
| 변경 가능 | `set()`으로 언제든 | 불변 |
| Virtual Thread 친화도 | 낮음 (Map 동시 생존 수 급증) | 높음 (자동 해제) |
| 자식 스레드 전파 | `InheritableThreadLocal` | `StructuredTaskScope`와 자동 통합 |

실제 서비스 코드에서 `ThreadLocal`을 `ScopedValue`로 옮길 때 생기는 세부 문제들(스케줄러나 이벤트 리스너처럼 HTTP 요청 밖에서 실행되는 코드의 컨텍스트 바인딩, 자식 스레드로의 전파 등)은 이 글의 범위를 벗어납니다. 관심이 있다면 [가상 스레드 적용기 - 플랫폼 스레드와 로컬 비교]({{< ref "4.md" >}}) 글을 참고해 주세요.

## 6. JDK 내부가 Virtual Thread를 받아들인 과정

Virtual Thread가 의미 있게 동작하려면 JDK 내부와 사용자 라이브러리가 non-blocking I/O에 대응하는 구조로 쓰여 있어야 합니다. JDK 팀은 몇 단계에 걸쳐 이걸 맞춰 왔습니다.

- **Java 13 (JEP 353)**: `java.net.Socket`, `ServerSocket`의 레거시 내부 구현을 `NioSocketImpl`로 재구현해 기본값으로 삼았습니다. 가상 스레드 도입 이전이지만, 뒤에 올 Poller 연동의 토대가 된 작업입니다.
- **Java 21**: 그 `NioSocketImpl`을 가상 스레드와 엮었습니다. 소켓이 내부적으로 non-blocking 모드로 동작하고, 데이터가 없으면 Poller에 등록한 뒤 `Continuation.yield()`로 Carrier를 풀어줍니다. 앞 절에서 설명한 메커니즘이 여기서 완성됐습니다.
- **Java 21~23**: `java.io`의 `BufferedInputStream` 같은 곳에서 `synchronized` 기반 내부 잠금을 명시적 락으로 교체했습니다. 당시 기준으로는 pinning 회피가 목적이었습니다.
- **Java 24 (JEP 491)**: `synchronized`가 더 이상 pinning을 일으키지 않게 되면서, 위의 리팩토링 노력과 사용자 측의 `ReentrantLock` 교체가 사후적으로 **불필요해진** 상태가 됐습니다. 외부 라이브러리(특히 JDBC 드라이버)에 남아 있던 `synchronized` 안의 I/O도 이 시점부터 자연히 풀립니다.

`java.util.concurrent`의 `ReentrantLock`, `Semaphore`, `CountDownLatch`, `CompletableFuture`, `BlockingQueue` 구현체들은 원래부터 `LockSupport.park()/unpark()` 기반이어서 Virtual Thread와 잘 맞습니다. 이 시기 동안 손댈 일이 없었던 영역이기도 합니다.

> 요약하면 JDK 21~23에서 겪었던 pinning 이슈의 대부분은 JDK 24+로 옮기는 것만으로 해결됩니다.

## 7. Virtual Thread가 모든 작업에 맞진 않는다

마지막으로 한 가지는 분명히 해 두겠습니다. **Virtual Thread는 I/O bound 작업에 맞는 기술이고, CPU bound 작업에는 맞지 않습니다.**

Virtual Thread의 이점은 I/O 대기 시간 동안 Carrier Thread를 해방시켜 다른 Virtual Thread를 실행하는 데 있습니다. CPU bound 작업은 I/O 대기가 없고 CPU를 계속 점유하므로, unmount할 시점 자체가 없습니다. 이 경우 동시에 실제로 돌아가는 수는 결국 **Carrier Thread 수(기본값: CPU 코어 수)** 로 제한되고, 남는 건 ForkJoinPool 스케줄링과 mount / unmount 비용 정도입니다. CPU bound 전용 작업은 그냥 코어 수만큼의 Platform Thread를 쓰는 게 낫습니다.

Virtual Thread가 빛을 발하는 자리는 요청 하나가 여러 번의 I/O를 수반하는 환경, 즉 웹 서버, API 게이트웨이, 마이크로서비스 간 통신입니다. Thread-per-Request 모델을 유지하면서도 스레드 풀 크기에 처리량이 묶이지 않는 것, 이것이 Virtual Thread의 실제 가치입니다.

## 마치며

정리하면 이 글이 다룬 건 이렇습니다. Virtual Thread는 개발자가 Blocking API를 그대로 쓰게 두고, 내부에서는 그걸 OS의 Non-blocking I/O로 바꿔 Carrier Thread를 비워 둡니다. 그 뒤에 숨어 있는 메커니즘을 정리하면 이렇습니다.

- JVM이 소켓을 non-blocking 모드로 변환하고, `Continuation.yield()`로 Virtual Thread를 unmount
- Poller 스레드가 `epoll`로 I/O 완료를 감지해 Virtual Thread를 다시 스케줄링
- ForkJoinPool의 work-stealing으로 Carrier Thread들이 균등하게 쓰이도록 유지
- JDK 21~23 시기 pinning의 정체와 JEP 491(JDK 24)이 이 문제를 어떻게 걷어냈는가

이 글은 "I/O 대기 시 자동으로 전환되고, 완료 시 자동으로 복귀하는" JVM 수준의 구현이 어떻게 성립하는지를 살펴본 **이론** 편입니다. 시리즈의 나머지는 이렇게 이어집니다. 더 아래 층의 원리(사용자 수준 스레드와 컨텍스트 스위칭 자체)를 C로 바이트 단위까지 직접 구현해 본 저수준 실습은 [가상 스레드는 어떻게 동작하는가 - C로 직접 구현해 보기]({{< ref "2.md" >}}) 글에, 같은 원리가 Spring 애플리케이션 위에서 플랫폼 스레드와 어떻게 갈리는지를 로컬에서 비교한 실습은 [가상 스레드 적용기 - 플랫폼 스레드와 로컬 비교]({{< ref "4.md" >}}) 글에, 그것을 운영 인프라에서 실측해 리소스 한계를 막은 트러블슈팅은 [“가상 스레드는 마음껏 만들어도 된다”, 운영에서 곧이곧대로 믿으면 생기는 일]({{< ref "5.md" >}}) 글에 정리해 두었습니다.

이 글이 Java Virtual Thread의 I/O 처리 방식을 이해하는 데 도움이 되었으면 합니다.
