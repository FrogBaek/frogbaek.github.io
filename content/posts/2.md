## 들어가며

Java 21에서 정식으로 도입된 Virtual Thread(가상 스레드)는 기존의 동시성 프로그래밍 모델을 근본적으로 바꾸는 기능입니다. `Thread.ofVirtual().start(...)` 한 줄이면 수십만 개의 스레드를 만들 수 있고, 기존의 블로킹 코드를 그대로 사용하면서도 논블로킹에 가까운 성능을 얻을 수 있습니다.

처음 이 기술을 접했을 때, 사용법 자체는 간단했지만 "어떻게 OS 스레드 없이 스레드를 만든다는 것인가?"라는 질문에는 답할 수가 없었습니다. JEP 444 문서를 읽어봐도 Continuation, Carrier Thread, ForkJoinPool 같은 용어들이 추상적으로 느껴질 뿐이었습니다.

그래서 직접 만들어 보기로 했습니다. Java Virtual Thread의 핵심 메커니즘인 **Green Thread**(사용자 수준 스레드)를 C 언어로 구현하면, 그 안에서 일어나는 일을 바이트 단위로 이해할 수 있을 것이라 생각했습니다.

이 글에서는 다음 내용을 다룹니다.

- OS 스레드(Platform Thread)의 구조적 한계는 무엇인가
- Green Thread의 핵심인 컨텍스트 스위칭을 C로 어떻게 구현하는가
- Java Virtual Thread가 이 원리를 어떻게 추상화하여 활용하는가

> **참고:** 이 글은 C 언어 수준까지만 구체적으로 다룹니다. 스택 포인터를 직접 교환하는 한 함수는 C만으로는 작성할 수 없어 어셈블리가 필요한데, 그 내부도 본질에 해당하는 다섯 줄만 짚고 플랫폼별 디테일(레지스터 개수, 인자 전달 규약, 스택 정렬 등)은 생략합니다. 이론 설명(스택 크기, 스레드 비용 등)은 Linux 기준입니다.

## 1. OS 스레드는 왜 한계가 있는가

Virtual Thread를 이해하려면, 먼저 기존의 OS 스레드(Platform Thread)가 왜 문제인지를 알아야 합니다.

### 1-1. 스레드 하나의 비용

Linux 기준으로 OS 스레드 하나를 생성하면 다음과 같은 자원이 소모됩니다.

| 항목 | 비용 |
|------|------|
| 스택 메모리 | 기본 8MB (ulimit -s로 확인 가능) |
| 커널 자원 | task_struct, 커널 스택, 파일 디스크립터 테이블 등 |
| 생성 비용 | `clone()` 시스템 콜 → 커널 모드 전환 필요 |
| 컨텍스트 스위칭 | 레지스터 저장/복구 + TLB 플러시 + 캐시 미스 |

스레드 1개에 스택만 8MB라면, 1,000개를 생성하면 스택으로만 약 8GB의 **주소 공간을 예약**하게 됩니다. 물론 이 8MB가 통째로 물리 메모리에 올라가는 건 아닙니다. 실제로 건드린 페이지만 그때그때 커밋되기 때문에, 1,000개를 만들었다고 곧바로 8GB를 점유하지는 않습니다. 그래도 주소 공간을 그만큼 잡아먹고, 여기에 페이지 테이블이나 뒤에서 볼 커널 자원까지 더해지면 스레드를 무한정 늘리기는 어렵습니다. 대부분의 서버 애플리케이션이 동시 스레드 수를 수백~수천 개 수준으로 제한하는 것도 이 때문입니다.

> 참고로 이 8MB는 Linux의 pthread 기본 스택 크기(`ulimit -s`)입니다. JVM이 만드는 스레드는 `-Xss`로 보통 512KB~1MB를 쓰기 때문에, 실제 자바 애플리케이션의 플랫폼 스레드는 이보다 작습니다. 이 글에서 8MB를 기준으로 삼는 건 원리를 또렷하게 보여 주기 위해서입니다.

### 1-2. Thread-per-Request 모델의 병목

전통적인 Java 서버(Spring MVC 등)는 **Thread-per-Request** 모델을 사용합니다. HTTP 요청 하나가 들어오면 스레드 하나를 할당하고, 응답이 완료될 때까지 해당 스레드가 점유됩니다.

![](/images/2/thread_blocking.png)

문제는 DB 쿼리, 외부 API 호출 같은 I/O 작업에서 스레드가 **아무 일도 하지 않으면서 점유**된다는 점입니다. CPU는 놀고 있는데 스레드 풀이 가득 차서 새 요청을 받지 못하는 상황이 발생합니다.

이 문제를 해결하기 위해 WebFlux 같은 리액티브 프레임워크가 등장했지만, 콜백 기반의 코드는 작성과 디버깅이 어렵고, 기존 블로킹 라이브러리(JDBC 등)와 호환되지 않는 문제가 있었습니다.

### 1-3. Virtual Thread의 접근

Java Virtual Thread의 접근은 명확합니다.

> **스레드의 비용을 극적으로 낮춰서, 스레드를 많이 만드는 것 자체를 해결책으로 삼는다.**

이를 위해 Virtual Thread는 OS 스레드를 직접 사용하지 않습니다. 대신 **사용자 공간(User Space)**에서 자체적으로 스레드를 관리합니다. 이것이 바로 Green Thread의 개념이며, Virtual Thread의 근간이 되는 기술입니다.

## 2. Green Thread란 무엇인가

Green Thread는 OS가 아닌 **애플리케이션(또는 런타임)이 직접 관리하는 스레드**입니다. OS 입장에서는 프로세스 안에서 무슨 일이 일어나는지 알지 못합니다. 단일 OS 스레드 위에서 여러 개의 Green Thread가 번갈아 실행되는 구조입니다.

![](/images/2/green_thread.png)

OS 스레드와 Green Thread의 핵심적인 차이는 다음과 같습니다.

| 구분 | OS 스레드 | Green Thread |
|------|-----------|-------------|
| 스택 크기 | 8MB (고정) | 수 KB ~ 수십 KB (가변) |
| 생성 비용 | 커널 모드 전환 필요 | malloc + 포인터 연산 |
| 컨텍스트 스위칭 | 커널이 수행 (수 us) | 사용자 코드에서 수행 (수십 ns) |
| 스케줄링 | OS 스케줄러 (선점형) | 애플리케이션 스케줄러 (협력형) |
| 개수 제한 | 수천 개 수준 | 수십만 ~ 수백만 개 |

> 위 표의 'Green Thread' 열은 개념(및 Java Virtual Thread에서의 실현)을 기준으로 한 것입니다. 이 글에서 직접 만들 C 구현은 이해를 위해 스택을 64KB로 **고정**하며, 개념상의 '가변 스택'과 구현 사이의 차이는 4-2절에서 다시 정리합니다.

이 차이의 핵심은 **스택을 어떻게 관리하는가**와 **컨텍스트 스위칭을 누가 하는가**에 있습니다. 이 두 가지를 C 언어로 직접 구현해 보겠습니다.

## 3. C로 Green Thread 구현하기

### 3-1. 전체 구조

구현할 Green Thread 시스템의 구조는 다음과 같습니다.

```
green_thread.h     ─ TCB 구조체, 상태 enum, API 선언
green_thread.c     ─ 스케줄러, 스레드 생성, yield (순수 C)
context_switch.S   ─ 레지스터 저장/복구 + 스택 전환 (짧은 어셈블리)
main.c             ─ 데모
```

코드의 대부분은 C이고, "현재 CPU의 레지스터를 스택에 밀어 넣고 스택 포인터 자체를 바꾸는" 한 함수(`context_switch`)만 C의 추상화 바깥에 있어 어셈블리로 작성합니다. 이 함수의 본체는 다섯 줄 정도로 끝나며, 3-3절에서 본질에 해당하는 부분만 추려 보여 드리겠습니다.

### 3-2. TCB (Thread Control Block) 설계

OS에서 PCB(Process Control Block)가 프로세스의 상태 정보를 관리하듯이, Green Thread도 각 스레드의 상태를 저장할 구조체가 필요합니다. 이것이 TCB(Thread Control Block)입니다.

```c
/* 스레드 상태 - OS의 프로세스 상태 전이도와 동일한 개념 */
typedef enum {
    READY,      /* 실행 대기 중 (스케줄러가 골라주길 기다리는 상태) */
    RUNNING,    /* 현재 CPU를 점유하고 실행 중 */
    FINISHED    /* 실행 완료 */
} ThreadState;

typedef struct {
    int         id;       /* 스레드 식별자 */
    ThreadState state;    /* 현재 상태 */
    void       *stack;    /* malloc으로 할당한 스택 메모리의 시작 주소 */
    void       *sp;       /* 저장된 스택 포인터 (컨텍스트 스위칭의 핵심) */
    void      (*entry)(void);  /* 이 스레드가 실행할 함수 포인터 */
} GreenThread;
```

이 구조체에서 가장 중요한 필드는 `sp`(스택 포인터)입니다. 컨텍스트 스위칭이 발생하면 현재 CPU의 레지스터 상태가 스택에 저장되고, 이 `sp`가 그 스택의 위치를 가리킵니다. 나중에 이 스레드로 돌아올 때, `sp`가 가리키는 곳에서 레지스터를 복구하면 중단된 지점부터 실행을 재개할 수 있습니다.

스택 크기는 64KB로 설정하였습니다.

```c
#define STACK_SIZE (1024 * 64)  /* 64KB */
```

OS 스레드의 기본 스택이 8MB(8,192KB)인 것과 비교하면, 같은 메모리로 128배 더 많은 Green Thread를 생성할 수 있다는 의미입니다. Java Virtual Thread가 수십만 개의 스레드를 만들 수 있는 것도 이와 동일한 원리입니다.

### 3-3. 컨텍스트 스위칭 - 이 프로젝트의 핵심

컨텍스트 스위칭은 **현재 실행 중인 스레드의 CPU 상태를 저장하고, 다른 스레드의 CPU 상태를 복구하는 작업**입니다. OS가 프로세스를 전환할 때 하는 일과 본질적으로 동일하지만, 이 구현에서는 커널이 아닌 사용자 공간에서 직접 수행합니다.

구체적으로 하는 일은 세 단계입니다.

1. **현재 스레드의 CPU 상태(callee-saved 레지스터)를 현재 스택에 저장한다.**
2. **스택 포인터를 새 스레드의 스택 포인터로 교체한다.** 이 순간부터 CPU는 완전히 다른 스택을 사용하게 됩니다.
3. **새 스택에서 CPU 상태를 복구한 뒤, 저장돼 있던 return address로 점프한다.**

세 단계 중 **2번이 이 프로젝트의 핵심**입니다. 스택 포인터 한 줄을 바꾸는 것이 "지금까지 실행 중이던 스레드"와 "이제부터 실행될 스레드"를 맞바꿉니다. 여기서 caller-saved 레지스터는 함수 호출 규약 덕분에 호출 시점에 이미 호출자가 저장해 뒀으니, 우리가 직접 챙겨야 하는 건 callee-saved 레지스터만으로 충분합니다.

문제는 이 세 단계가 **C 언어로는 직접 작성할 수 없다**는 점입니다. 현재 CPU의 레지스터를 임의로 스택에 밀어 넣고 스택 포인터 자체를 바꾸는 조작은 C의 추상화 바깥에 있어서, `context_switch` 함수 한 개만은 어셈블리로 작성합니다. C 쪽에서는 다음 시그니처로 호출합니다.

```c
/*
 * 현재 스레드의 상태를 저장하고, 새 스레드로 전환한다.
 *   old_sp: 현재 스택 포인터를 저장할 위치
 *   new_sp: 이제부터 사용할 스레드의 스택 포인터
 */
extern void context_switch(void **old_sp, void *new_sp);
```

어셈블리 본체도 짧습니다. 플랫폼별 디테일(callee-saved 레지스터 개수, 인자 전달 규약 등)을 걷어내면 본질은 다음 다섯 줄입니다.

```asm
context_switch:
    push  <callee-saved 레지스터들>   ; (1) 현재 CPU 상태를 현재 스택에 저장
    mov   [old_sp], sp                ; (2-a) 현재 sp 를 *old_sp 에 백업
    mov   sp, new_sp                  ; (2-b) sp 를 new_sp 로 교체
    pop   <callee-saved 레지스터들>   ; (3-a) 새 스택에서 CPU 상태 복구
    ret                               ; (3-b) 새 스택 최상단의 주소로 점프
```

`ret` 한 줄이 이 구현의 핵심입니다. 일반 함수에서는 호출자에게 돌아가는 평범한 명령이지만, 여기서는 그 직전에 스택을 바꿔치기했기 때문에 "새 스택이 가리키고 있던 어딘가의 실행 지점"으로 점프합니다. 그 지점이 바로 이전에 해당 스레드가 `context_switch`를 호출했던 자리이고, 호출자 관점에서는 마치 `context_switch`가 방금 반환된 것처럼 이어집니다.

플랫폼에 따라 달라지는 부분(실제로 어떤 레지스터가 callee-saved인지, 인자가 어느 레지스터로 들어오는지, 스택 정렬은 몇 바이트 경계인지)은 호출 규약 문서를 보고 맞춰 주면 되는 기계적인 일이고, 이 글의 주제는 아니므로 여기서는 생략합니다.

### 3-4. 스레드 생성 - 초기 스택 프레임 구성

스레드를 "생성"한다는 것은, **나중에 `context_switch`로 전환했을 때 마치 처음부터 그 함수가 실행되는 것처럼 스택을 미리 세팅해두는 것**을 의미합니다.

`context_switch`는 마지막에 "저장된 callee-saved를 복구하고 return address로 점프"하는 것으로 끝납니다. 따라서 새 스레드의 초기 스택을 다음 모양으로 만들어 두면, 최초 전환 시 복구와 점프가 일어나면서 `thread_wrapper` 함수로 들어가며 스레드가 시작됩니다.

![](/images/2/thread_create.png)

callee-saved 슬롯을 몇 개 쌓아 둘지는 플랫폼/ABI에 따라 다르지만, 어느 플랫폼이든 `context_switch`가 복구하는 개수와 같게 맞춰 두면 됩니다. 이 글에서는 그 개수를 `NUM_CALLEE_SAVED`라는 상수로 표현하겠습니다.

이것을 C 코드로 구현하면 다음과 같습니다.

```c
int green_thread_create(void (*func)(void)) {
    if (thread_count >= MAX_THREADS) {
        fprintf(stderr, "error: 최대 스레드 수(%d) 초과\n", MAX_THREADS);
        return -1;
    }

    GreenThread *t = &threads[thread_count];
    t->id = thread_count;
    t->state = READY;
    t->entry = func;

    /* 스택 메모리 할당 */
    t->stack = malloc(STACK_SIZE);
    if (!t->stack) {
        fprintf(stderr, "error: 스택 메모리 할당 실패\n");
        return -1;
    }

    /*
     * 스택은 높은 주소 → 낮은 주소 방향으로 자란다.
     * 그래서 할당한 메모리의 "끝"부터 시작해서 sp를 감소시키며 채운다.
     * (호출 규약이 요구하는 스택 정렬 같은 플랫폼 디테일은 생략.)
     */
    void **sp = (void **)((char *)t->stack + STACK_SIZE);

    /* (1) context_switch 복구 단계의 마지막 ret 이 점프할 주소 */
    *(--sp) = (void *)thread_wrapper;

    /* (2) callee-saved 레지스터 초기값 슬롯: 전부 0 으로 채운다.
     *     context_switch 가 복구 단계에서 여기서 값을 꺼내 쓴다. */
    for (int i = 0; i < NUM_CALLEE_SAVED; i++) {
        *(--sp) = 0;
    }

    t->sp = sp;

    return thread_count++;
}
```

여기서 핵심 포인트를 짚겠습니다.

**이 "스택"은 사실 힙 메모리다**

먼저 분명히 할 점이 있습니다. `t->stack = malloc(STACK_SIZE)`로 잡은 이 64KB는 **물리적으로는 힙 메모리**입니다. OS가 `main`·스케줄러에게 준 "진짜" 스택과는 완전히 별개로, 힙에서 떼어 온 블록을 우리가 *스택처럼* 쓰는 것뿐입니다. (Java Virtual Thread가 스택 프레임을 힙에 두는 것도 같은 발상이며, 4-2절에서 다시 다룹니다.)

![](/images/2/process_memory.png)

**그 64KB 블록을 어느 방향으로 채우는가**

이제 떼어 온 블록 *내부*를 봅니다. x86/ARM을 포함한 주요 아키텍처에서 스택은 높은 주소에서 낮은 주소 방향으로 자라며, 값을 쌓을 때마다 스택 포인터가 감소합니다. 따라서 이 블록을 스택처럼 쓰려면 **끝 주소**(= 높은 주소)에서부터 `--sp`로 값을 채워 넣어야 합니다.

![](/images/2/green_thread_block.png)

**`thread_wrapper`가 필요한 이유**

스레드 함수(`entry`)를 직접 실행하지 않고 `thread_wrapper`를 거치는 이유는, 스레드 함수가 `return`했을 때 **그 다음에 무엇을 해야 하는지** 정해줘야 하기 때문입니다.

```c
static void thread_wrapper(void) {
    threads[current_thread].entry();     /* 스레드 함수 실행 */
    threads[current_thread].state = FINISHED;

    /* 스레드 함수 종료 → 스케줄러로 복귀 */
    context_switch(&threads[current_thread].sp, scheduler_sp);
}
```

OS 스레드는 함수가 끝나면 `pthread_exit()`가 자동으로 호출되지만, Green Thread에는 그런 메커니즘이 없습니다. `thread_wrapper`가 없다면, 스레드 함수가 return한 뒤 `context_switch`가 세워 둔 초기 스택의 바깥으로 흘러나가면서 쓰레기 값을 return address로 삼아 점프해 segfault가 납니다.

### 3-5. 스케줄러 - 라운드 로빈

스케줄러는 READY 상태인 스레드를 순서대로 하나씩 실행시키고, 스레드가 `yield`하거나 종료되면 다음 스레드로 넘어가는 역할을 합니다.

```c
void scheduler_run(void) {
    while (1) {
        int found = 0;

        for (int i = 0; i < thread_count; i++) {
            if (threads[i].state != READY)
                continue;

            found = 1;
            current_thread = i;
            threads[i].state = RUNNING;

            /*
             * 여기서 context_switch를 호출하면:
             *   1) 스케줄러의 현재 상태(레지스터)가 scheduler_sp에 저장됨
             *   2) threads[i]의 저장된 상태가 복구되면서 해당 스레드 실행 재개
             *
             * 그리고 나중에 그 스레드가 yield()하면:
             *   1) 스레드의 상태가 다시 저장됨
             *   2) scheduler_sp가 복구되면서 바로 아래 줄로 돌아옴
             */
            context_switch(&scheduler_sp, threads[i].sp);

            /*
             * 여기로 돌아왔다는 건 스레드가 yield()했거나 종료된 것.
             * 종료됐으면 thread_wrapper에서 이미 FINISHED로 바꿔놨고,
             * yield였으면 아직 RUNNING이니까 다시 READY로 바꿔준다.
             */
            if (threads[i].state == RUNNING) {
                threads[i].state = READY;
            }
        }

        /* READY인 스레드가 하나도 없으면 전부 끝난 것 */
        if (!found) break;
    }

    /* 정리: 할당한 스택 메모리 해제 */
    for (int i = 0; i < thread_count; i++) {
        free(threads[i].stack);
        threads[i].stack = NULL;
    }
}
```

여기서 `scheduler_sp`의 역할이 중요합니다. 이 변수는 **스케줄러 자신의 실행 상태**를 저장하는 곳입니다. 스레드가 `yield()`를 호출하면 스레드의 상태가 저장되고, `scheduler_sp`에 백업해둔 스케줄러의 상태가 복구되면서 `context_switch` 호출 바로 다음 줄로 돌아옵니다.

이 `scheduler_sp`는 Java Virtual Thread에서 **Carrier Thread**의 역할과 정확히 대응됩니다. Carrier Thread는 Virtual Thread를 실행하는 실제 OS 스레드이며, Virtual Thread가 중단(yield/block)되면 Carrier Thread가 제어권을 되찾아 다음 Virtual Thread를 실행합니다.

### 3-6. yield - 자발적 양보

```c
void green_thread_yield(void) {
    context_switch(&threads[current_thread].sp, scheduler_sp);
}
```

`yield()`는 단 한 줄입니다. 현재 스레드의 상태를 저장하고, 스케줄러로 돌아갑니다.

Java의 `Thread.yield()`와 개념이 같지만, Virtual Thread에서는 `yield`뿐 아니라 **I/O 블로킹 시에도 자동으로 이 동작이 일어난다**는 점이 핵심적인 차이입니다. `Socket.read()`, `Thread.sleep()` 같은 블로킹 메서드를 호출하면 JVM 내부에서 `Continuation.yield()`가 호출되어 해당 Virtual Thread가 Carrier Thread에서 분리(unmount)됩니다. 개발자는 평소처럼 블로킹 코드를 작성하면 되고, JVM이 알아서 논블로킹으로 처리해주는 것입니다.

### 3-7. 실행 결과

세 개의 Green Thread를 만들어 번갈아 실행시키는 데모 코드입니다.

```c
void task_a(void) {
    for (int i = 0; i < 5; i++) {
        printf("[스레드 A] 작업 중... (%d/5)\n", i + 1);
        green_thread_yield();
    }
    printf("[스레드 A] 완료!\n");
}

void task_b(void) {
    for (int i = 0; i < 3; i++) {
        printf("[스레드 B] 작업 중... (%d/3)\n", i + 1);
        green_thread_yield();
    }
    printf("[스레드 B] 완료!\n");
}

void task_c(void) {
    for (int i = 0; i < 4; i++) {
        printf("[스레드 C] 작업 중... (%d/4)\n", i + 1);
        green_thread_yield();
    }
    printf("[스레드 C] 완료!\n");
}

int main(void) {
    scheduler_init();

    green_thread_create(task_a);
    green_thread_create(task_b);
    green_thread_create(task_c);

    scheduler_run();

    printf("모든 스레드 실행 완료.\n");
    return 0;
}
```

실행 결과는 다음과 같습니다.

```
[스레드 A] 작업 중... (1/5)
[스레드 B] 작업 중... (1/3)
[스레드 C] 작업 중... (1/4)
[스레드 A] 작업 중... (2/5)
[스레드 B] 작업 중... (2/3)
[스레드 C] 작업 중... (2/4)
[스레드 A] 작업 중... (3/5)
[스레드 B] 작업 중... (3/3)
[스레드 C] 작업 중... (3/4)
[스레드 A] 작업 중... (4/5)
[스레드 B] 완료!
[스레드 C] 작업 중... (4/4)
[스레드 A] 작업 중... (5/5)
[스레드 C] 완료!
[스레드 A] 완료!

```

OS 스레드는 `main`이 실행되는 **단 1개**뿐이지만, 3개의 Green Thread가 번갈아 실행되면서 마치 동시에 실행되는 것처럼 보입니다. `yield()`를 호출할 때마다 컨텍스트 스위칭이 발생하여 다음 스레드로 전환되고, 자기 차례가 다시 오면 `yield()` 다음 줄부터 이어서 실행됩니다.

이것이 바로 Java Virtual Thread에서 `Continuation`이 하는 일입니다. 실행을 중단했다가, 나중에 중단된 지점부터 다시 재개하는 것입니다.

### 3-8. 이 구현이 할 수 없는 것 - 협력형 스케줄링의 한계

여기까지의 구현은 **순수 협력형(cooperative)**입니다. 스레드가 `green_thread_yield()`를 명시적으로 호출해야만 전환이 일어납니다. 바꿔 말하면, 어느 스레드 하나가 `yield()`를 부르지 않고 무한 루프에 들어가면 같은 carrier 위의 모든 Green Thread가 그대로 멈춰버립니다. OS 스케줄러가 시간 슬라이스로 강제 선점(preemption)해 주는 보호 장치가 여기엔 없기 때문입니다.

또 하나, 이 구현은 **blocking I/O를 처리할 수 없습니다.** `read()`나 `sleep()` 같은 시스템 콜을 호출하는 순간 OS 스레드가 통째로 blocking되고, 그 위의 Green Thread들도 함께 멈춥니다. 사용자 공간 스케줄러가 "I/O는 잠깐 기다리니까 다른 Green Thread를 먼저 돌리자"를 알아서 해 주려면, 소켓을 non-blocking 모드로 바꾸고 `epoll` 같은 이벤트 메커니즘에 fd를 등록한 뒤 I/O 완료 통지를 받으면 해당 Green Thread를 다시 스케줄링하는 별도의 런타임 층이 필요합니다.

Java Virtual Thread가 이 두 가지 한계를 어떻게 넘는지는 이 글의 범위를 벗어납니다. JVM 수준의 해결 방식이 궁금하다면 [가상 스레드는 어떻게 I/O를 처리하는가 - blocking API의 내부 동작 원리]({{< ref "3.md" >}}) 글을 참고해 주세요.

## 4. Java Virtual Thread와의 연결

C로 Green Thread를 직접 구현해 보았으니, 이제 Java Virtual Thread가 이 원리를 어떻게 활용하는지 대응 관계를 정리하겠습니다.

### 4-1. 구성 요소 매핑

| C 구현 (이 프로젝트) | Java Virtual Thread | 역할 |
|---|---|---|
| `GreenThread` 구조체 (TCB) | `VirtualThread` 객체 | 스레드의 상태와 실행 정보를 저장 |
| `scheduler_sp` | Carrier Thread (ForkJoinPool의 Worker Thread) | Green Thread/Virtual Thread를 실제로 실행하는 OS 스레드 |
| `context_switch()` | `Continuation.yield()` / `Continuation.run()` | 실행 상태를 저장하고 복구하는 핵심 메커니즘 |
| `green_thread_yield()` | I/O 블로킹 시 JVM이 자동 호출 | 현재 스레드를 중단하고 스케줄러로 복귀 |
| `scheduler_run()` (라운드 로빈) | `ForkJoinPool` (work-stealing) | 실행 가능한 스레드를 골라서 Carrier Thread에 배정 |
| `malloc(STACK_SIZE)` 고정 할당 | 힙 메모리에 동적 스택 (초기 수백 바이트) | 스레드별 스택 메모리 관리 |

### 4-2. 우리 구현과 Java Virtual Thread의 차이

이 프로젝트는 Green Thread의 핵심 원리를 이해하기 위한 구현이며, Java Virtual Thread는 여기에 여러 최적화와 기능이 추가되어 있습니다. 주요 차이점을 정리하면 다음과 같습니다.

**스택 관리**

이 프로젝트에서는 스레드 생성 시 `malloc(64KB)`로 고정 크기 스택을 할당합니다. 반면 Java Virtual Thread는 **힙 메모리에 스택 프레임을 동적으로 할당**합니다. 처음에는 수백 바이트만 사용하다가, 함수 호출이 깊어지면 필요한 만큼 늘어납니다. 이 덕분에 수십만 개의 Virtual Thread를 생성해도 메모리 부담이 적습니다.

**스케줄링**

이 프로젝트의 스케줄러는 단순한 라운드 로빈 방식입니다. Java Virtual Thread는 `ForkJoinPool`의 **work-stealing 알고리즘**을 사용합니다. 여러 개의 Carrier Thread(기본값: CPU 코어 수)가 각자의 큐에서 Virtual Thread를 꺼내 실행하되, 자기 큐가 비면 다른 Carrier Thread의 큐에서 작업을 훔쳐옵니다. 이 방식은 M:N 매핑(여러 Virtual Thread를 여러 OS 스레드에 분배)을 가능하게 합니다.

**I/O 블로킹 처리**

이 프로젝트에서는 `yield()`를 명시적으로 호출해야 스레드가 전환됩니다. Java Virtual Thread에서는 `Socket.read()`, `Thread.sleep()`, `BlockingQueue.take()` 같은 블로킹 API를 호출하면 **JVM이 자동으로 `Continuation.yield()`를 호출**합니다. 개발자는 기존의 블로킹 코드를 그대로 작성하면 되고, JVM이 내부적으로 비동기 처리를 합니다.

**Pinning**

Virtual Thread가 Carrier Thread에서 unmount되지 못하고 고정(pin)되는 현상이 과거 버전에서 이슈였는데, JDK 24의 [JEP 491](https://openjdk.org/jeps/491) 이후로 대부분 해결되었습니다. 자세한 원인과 경위는 이 글의 범위를 벗어나므로 [가상 스레드는 어떻게 I/O를 처리하는가 - blocking API의 내부 동작 원리]({{< ref "3.md" >}}) 글에서 다룹니다.

### 4-3. Java 코드와의 비교

우리가 C로 구현한 것과 동일한 동작을 Java Virtual Thread로 작성하면 다음과 같습니다.

```java
public class VirtualThreadDemo {
    public static void main(String[] args) throws InterruptedException {
        Thread t1 = Thread.ofVirtual().start(() -> {
            for (int i = 0; i < 5; i++) {
                System.out.println("[스레드 A] 작업 중... (" + (i+1) + "/5)");
                Thread.yield();
            }
            System.out.println("[스레드 A] 완료!");
        });

        Thread t2 = Thread.ofVirtual().start(() -> {
            for (int i = 0; i < 3; i++) {
                System.out.println("[스레드 B] 작업 중... (" + (i+1) + "/3)");
                Thread.yield();
            }
            System.out.println("[스레드 B] 완료!");
        });

        Thread t3 = Thread.ofVirtual().start(() -> {
            for (int i = 0; i < 4; i++) {
                System.out.println("[스레드 C] 작업 중... (" + (i+1) + "/4)");
                Thread.yield();
            }
            System.out.println("[스레드 C] 완료!");
        });

        t1.join();
        t2.join();
        t3.join();
    }
}
```

Java 코드에서는 TCB도, 스택 할당도, 컨텍스트 스위칭도 전부 보이지 않습니다. 하지만 내부적으로는 이 글에서 C로 구현한 것과 본질적으로 같은 일이 일어나고 있습니다.

- `Thread.ofVirtual().start(...)` → `green_thread_create()`: 작은 스택을 할당하고 TCB를 초기화
- `Thread.yield()` → `green_thread_yield()`: Continuation 상태를 저장하고 Carrier Thread로 복귀
- ForkJoinPool → `scheduler_run()`: 다음 실행할 Virtual Thread를 골라서 Carrier Thread에서 실행

## 마치며

이 프로젝트의 전체 소스 코드는 약 300줄입니다. 이 안에 OS 수준의 컨텍스트 스위칭, 사용자 공간 스케줄링, 스택 관리라는 운영체제의 핵심 개념이 모두 담겨 있습니다.

Java Virtual Thread는 이 원리 위에 동적 스택 관리, work-stealing 스케줄러, JVM 수준의 자동 yield라는 고도화된 기능을 추가한 것입니다. `Thread.ofVirtual().start(...)`라는 간결한 API 뒤에서 이런 일들이 일어나고 있다는 것을 알고 사용하는 것과, 모르고 사용하는 것은 분명히 다를 것이라 생각합니다.

Blocking I/O 처리 메커니즘과 M:N 스레딩 모델에서의 동기화는 이 글의 범위를 벗어나 다루지 않았습니다. 이 글은 시리즈에서 **가상 스레드의 원리를 C로 직접 구현해 보는 저수준 실습**에 해당합니다. 그 원리의 이론적인 설명(JVM이 blocking API를 non-blocking으로 변환하는 메커니즘 등)은 [가상 스레드는 어떻게 I/O를 처리하는가 - blocking API의 내부 동작 원리]({{< ref "3.md" >}}) 글에 정리해 두었고, 같은 원리가 Spring 애플리케이션 위에서 플랫폼 스레드와 어떻게 갈리는지를 로컬에서 비교한 실습은 [가상 스레드 적용기 - 플랫폼 스레드와 로컬 비교]({{< ref "4.md" >}}) 글에, 그것을 운영 인프라에서 실측해 리소스 한계를 막은 트러블슈팅은 [“가상 스레드는 마음껏 만들어도 된다”, 운영에서 곧이곧대로 믿으면 생기는 일]({{< ref "5.md" >}}) 글에 있습니다.

이 글이 Java Virtual Thread의 동작 원리를 이해하는 데 도움이 되었으면 합니다.
