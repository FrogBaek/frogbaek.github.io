## 들어가며

가상 스레드로 돌아가는 백엔드의 리소스 보호 값을 정하느라 한참 씨름한 기록입니다.

구체적으로는 이런 문제였습니다. 소셜 로그인·푸시 발송 같은 외부 API 호출이 몰리면, 무한정 만들어지는 가상 스레드가 개수가 정해진 HTTP 커넥션 풀을 한꺼번에 차지해 풀을 고갈시킵니다. 그래서 외부로 나가는 길목마다 세마포어로 동시 호출 수를 묶고, 사용자가 기다리는 소셜 로그인은 제때 허가를 얻지 못하면 ~500ms 만에 거절하게 했습니다. 그런데 나가는 쪽을 다 막아도 한 군데가 더 남았습니다. 요청이 들어오는 쪽의 한계입니다. 이 글은 그 두 한계를 부하 테스트로 직접 측정해 값을 정한 기록이고, 그 과정에서 이 부하에서 가장 먼저 닿은 천장이 미리 짐작한 외부 세마포어가 아니라 한 층 안쪽이었다는 것까지 따라갑니다.

가상 스레드를 마음껏 만들어도 되는 건 *만드는* 비용에 한정된 이야기입니다. 가상 스레드 생성 자체는 힙 객체 하나를 할당하는 수준이라 싸고, 블로킹 I/O를 만나면 캐리어 스레드(실제 OS 스레드)를 반납하니까 대기하는 동안 OS 스레드도 잡지 않습니다. 하지만 그렇게 만들어진 스레드가 건드리는 외부 리소스와 그 스레드를 받아들이는 서버 입구에는 여전히 유한한 한계가 남습니다. 그러면 자연히 이런 질문이 남습니다. "그래서 운영에선 그 한계 값을 얼마로 잡아야 하지?" 이 값은 책상에서 계산만 해서는 안 나옵니다(그 이유는 3장에서 짚습니다). 이 글은 그 질문 하나를 들고 부하 테스트로 두 군데의 처리 한계(밖으로 나가는 쪽과 안으로 들어오는 쪽) 값을 직접 측정해 정하고 그 과정에서 부딪힌 트러블슈팅을 정리한 기록입니다.

가상 스레드의 내부 동작(컨텍스트 스위칭과 스택 관리, 블로킹 API가 JVM 안에서 논블로킹 I/O로 바뀌는 메커니즘)이나 플랫폼 스레드와의 성능 비교 자체는 이미 잘 알려져 있으니, 이 글에서는 그 원리를 반복하지 않고 "운영에서 한계 값을 어떻게 쟀는가"라는 실측 한 건에만 집중하겠습니다. 이해에 필요한 최소한의 배경은 그때그때 본문에서 짚겠습니다.

## 1. 프로젝트 환경 - 한 프로세스에 사는 모놀리스

뒤 내용을 이해하려면 이 서비스가 물리적으로 어떻게 생겼는지부터 봐야 합니다.

이 프로젝트는 통신사/카드사 같은 곳의 혜택 정보를 자동으로 수집·파싱해서 사용자에게 개인화 피드와 알림으로 보내 주는 Spring Boot 백엔드입니다. 여기서 짚어 둘 건 이게 모놀리스라는 점입니다. 아래 세 종류의 작업이 하나의 JVM 프로세스 안에서 같이 돕니다.

| 작업 | 성격 | 무엇을 호출하나 |
|---|---|---|
| 사용자 API | 동기 요청 (혜택 조회, 소셜 로그인) | DB, 카카오/네이버 OAuth |
| 스케줄러(배치) | 시간 기반 비동기 작업 (스크래핑·파싱·알림 발송·정리) | 헤드리스 브라우저, 외부 HTTP, 외부 AI, 푸시(FCM) |
| Admin 서버 | 운영자용 동기 요청 (검수·재처리) | DB, 파싱 파이프라인 |

`spring.threads.virtual.enabled=true` 한 줄이면 Tomcat 워커, `@Async`, `@Scheduled`가 전부 같은 가상 스레드 모델 위에서 돕니다. 그 말은 캐리어 스레드 풀(ForkJoinPool)도, 힙도, Tomcat 커넥터도 이 세 작업이 같이 쓴다는 뜻입니다.

캐리어 풀로 쓰이는 ForkJoinPool은 가상 스레드를 이렇게 스케줄링합니다. 가상 스레드가 블로킹을 만나 캐리어에서 내려오면(park), 그 캐리어는 놀지 않고 work stealing 방식으로 다른 큐에 밀린 작업을 가져와 실행합니다. 이렇게 캐리어를 쉬지 않고 굴려 적은 수의 OS 스레드로 많은 가상 스레드를 처리하는데, 바꿔 말하면 세 작업이 이 캐리어 풀 하나를 통째로 공유한다는 뜻이기도 합니다.

이 "한 프로세스에서 다 같이 쓴다"는 게 이번 트러블슈팅의 전제입니다. 새벽에 스크래핑 스케줄러가 헤드리스 브라우저를 띄우고, 주기적으로 알림 발송 스케줄러가 많은 사용자에게 푸시를 쏘고, 그 사이에 사용자가 소셜 로그인을 시도하는데, 이 전부가 같은 캐리어, 같은 힙, 같은 외부 자원(DB 커넥션, 외부 API 호출 한도)을 두고 경쟁합니다. 마이크로서비스였다면 작업별로 인스턴스가 분리돼서 한쪽이 터져도 다른 쪽까지 안 번졌을 텐데, 모놀리스에는 그 격리가 없습니다. 한 작업이 자원을 무한정 빨아들이면 나머지 둘이 같이 무너집니다.

가상 스레드를 쓴다고 이 위험이 줄어들진 않습니다. 형태만 바뀝니다. 플랫폼 스레드 모델이었다면 스레드 풀 크기가 "동시에 몇 개의 작업이 외부를 두드릴 수 있는가"를 자연스럽게 묶어 줬을 텐데(이 자기 보호 구조는 5장에서 다시 짚습니다), 가상 스레드에는 동시성을 묶어 주던 그 워커 풀이 없어서 무한정 생성이 곧 무한정 외부 호출이 되는 구조가 됩니다.

## 2. 문제 ① - 밖으로 나가는 호출의 처리 한계

### 2-1. 처음 한계가 드러난 곳 - 푸시 알림 발송

가장 먼저 한계에 부딪힌 건 푸시 알림 발송 스케줄러였습니다. 새 혜택이 등록되면 관심 사용자에게 푸시를 보내는 배치인데, 코드는 가상 스레드 교과서에 나올 법한 형태 그대로였습니다.

```java
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    for (var task : tasks) {
        executor.submit(task);   // 작업 하나당 가상 스레드 1개
    }
}
```

`newVirtualThreadPerTaskExecutor()`는 작업 하나당 가상 스레드 하나를 만듭니다. 발송 대상이 수백 개면 가상 스레드도 수백 개가 그 자리에서 생기고, 각 스레드는 안에서 푸시 서버(FCM)로 네트워크 호출을 합니다. 전부 외부로 나가는 I/O입니다.

여기서 무슨 일이 벌어지는지 보겠습니다. 가상 스레드 생성 자체는 앞서 말했듯 힙 객체 하나를 할당하는 수준이라 싸고, 블로킹 I/O를 만나면 캐리어를 반납하니까 대기하는 동안 OS 스레드도 안 잡습니다. 거기까지는 그대로 맞습니다. 문제는 그 다음에 있습니다.

만드는 비용이 0에 가깝다는 게, 만든 뒤 그 스레드가 두드리는 외부 리소스도 무한하다는 뜻은 아닙니다.

푸시 서버는 프로젝트당 전송 한도가 있고, 우리 쪽 HTTP 클라이언트도 커넥션 풀이 유한합니다. 수백 개의 가상 스레드가 동시에 푸시 서버로 쏟아지면 이렇게 됩니다.

1. **속도를 늦추라는 신호가 사라진다**: 크기가 정해진 풀은 작업이 상한을 넘으면 큐가 차고, 그 막힘이 곧 "지금은 더 못 받는다"는 신호가 돼서 보내는 쪽이 속도를 줄입니다. 그런데 가상 스레드를 무한정 만들면 이 신호가 사라집니다. 작업은 전부 즉시 받아들여지고, 압력은 조용히 다음 단계(푸시 서버 한도, 쌓이는 대기 스레드, GC)로 떠밀립니다. 보내는 쪽은 응답 지연이 폭증하거나 메모리가 터지고 나서야 뒤늦게 압니다.
2. **모놀리스라 같이 번진다**: 1장에서 말한 대로 이 전부가 사용자 API와 같은 힙, 같은 캐리어에서 벌어집니다. 알림 배치가 힙을 잡아먹으면 그 시간대에 로그인하던 사용자의 응답 지연이 같이 튑니다.

### 2-2. 같은 패턴이 소셜 로그인에도 있었다

푸시 발송은 스케줄러라 사용자가 직접 체감하진 않지만, 소셜 로그인은 사용자가 기다리는 동기 경로입니다. 카카오/네이버 사용자 정보 API를 호출하는데, HTTP 커넥션 풀만으로 동시성을 제어하면 미묘한 문제가 생깁니다.

커넥션 풀이 N개면, 동시 로그인이 N을 넘는 순간 나머지는 커넥션을 기다리며 줄을 섭니다. 문제는 줄 선 요청 하나하나가 대기 중에도 서버의 처리 자원(클라이언트 소켓, Tomcat이 처리 중으로 붙잡아 둔 연결, 그 요청이 올린 힙)을 그대로 쥐고 있다는 점입니다. 가상 스레드는 무한정 만들어지니 이 줄이 상한 없이 길어지고, 그만큼 서버의 처리 자원이 로그인 대기자로 채워지며 메모리와 GC를 짓누릅니다. 그 결과 OAuth와 아무 상관 없는 빠른 요청(예: 캐시에 바로 적중하는 혜택 조회)까지 처리 자원을 얻지 못해 같이 느려집니다. 느린 외부 호출 하나가 자기 경로를 넘어 서버 전체로 번지는 것이죠. 이 처리 자원의 상한 문제는 3장에서 본격적으로 다룹니다.

## 3. 문제 ② - 안으로 들어오는 요청의 입구 한계

### 3-1. 밖을 다 막아도 입구가 남는다

문제 ①만 해결하면 끝인 줄 알았습니다. 그런데 그 대책을 설계하다 보니 곧 걸리는 게 있었습니다. 세마포어로 막는 건 밖으로 나가는 호출 수인데, 서버 안으로 들어와서 그 세마포어 앞에 줄 서는 요청 수는 아무것도 막지 않는다는 점이었습니다. 나가는 쪽을 아무리 잘 묶어도, 요청이 들어오는 입구 쪽에 독립적인 한계가 하나 더 남아 있었습니다.

왜 그런지 보려고, 가상 스레드가 요청 입구에서 뭘 바꿨는지 들여다봤습니다.

**플랫폼 스레드 모델에서의 입구:**

```
요청 → Tomcat accept → 워커 스레드 풀(maxThreads=N) 에서 1개 점유 → 처리 → 반납
                          └─ N 개가 다 차면 그 다음 요청은 대기
                             (= 풀이 자연스럽게 입구를 막아 줌)
```

플랫폼 스레드 모델에서는 `maxThreads`가 곧 동시에 처리 중인 요청 수의 하드 상한입니다. 요청 하나가 OS 스레드 하나를 1:1로 점유하니까, 풀이 다 차면 그 이상은 물리적으로 못 들어옵니다. 스레드 풀이 곧 입구 역할을 했던 셈입니다.

**가상 스레드 모델에서의 입구:**

```
요청 → Tomcat accept → 요청마다 새 가상 스레드 생성 → 처리
                          └─ "풀이 차서 막힌다" 는 개념이 없음
                             maxThreads 가 입구 역할을 못 함
```

Spring Boot가 Tomcat 실행기를 가상 스레드로 바꾸면, 요청마다 새 가상 스레드를 만들어 주니까 `maxThreads`가 사실상 무의미해집니다. 그러면 입구를 막는 건 뭐가 남느냐. `server.tomcat.max-connections` 하나만 남습니다. Tomcat이 동시에 받아들이는 TCP 연결 수의 하드 상한입니다.

문제는 이 값의 기본값이 8192라는 점이었습니다. 작은 인스턴스에서 이 값은 입구를 막아 주는 게 아니라 사실상 서버를 통째로 죽이는 값에 가깝습니다. 8천 개가 넘는 요청이 동시에 처리 중이 되면, 외부 호출은 세마포어가 잘 묶어 줘도 그 8천 개가 전부 힙에 올라앉아 메모리가 터지기 때문입니다. 그래서 이 기본값을 그대로 둘 수는 없었습니다. 어떤 값으로 잡아야 안전한지는 4장에서 부하 테스트로 정합니다.

### 3-2. 왜 이게 안으로 들어오는 문제인가

문제 ①이 밖으로 나가는 동시 호출 수의 한계라면, 문제 ②는 안으로 들어와서 동시에 처리 중인 요청 수의 한계입니다. 이 둘은 독립적입니다. 외부 제한 장치를 아무리 잘 세워도, 수천 개의 요청이 동시에 처리 중이면 이렇게 됩니다.

- 각 요청은 가상 스레드 + 요청 객체 + (외부 제한 장치 앞에서 대기 중이라면) 대기 상태의 스레드 정보를 힙에 들고 있습니다.
- 이게 전부 외부 제한 장치 앞에 줄을 서면, 외부 호출 자체는 잘 묶였어도 줄 서 있는 동안의 힙 점유가 인스턴스 메모리를 넘깁니다.
- 힙이 차면 GC가 쉴 새 없이 돌고, 결국 메모리가 터져서 프로세스가 죽습니다.

즉 외부 제한 장치는 나가는 수를 묶지만, 들어와서 그 앞에 줄 서 있는 수는 안 묶습니다. 그 줄의 길이를 묶는 건 오직 `max-connections`입니다. 외부 세마포어와 Tomcat `max-connections`는 서로를 대체할 수 없는, 독립적인 두 장치입니다. 한계가 두 군데라고 말한 게 이래서입니다.

### 3-3. 그래서 값을 얼마로?

문제 ①의 세마포어 값들도, 문제 ②의 `max-connections` 값도, 결국 이 인스턴스 스펙이 감당 가능한 만큼이어야 합니다. 그런데 그 "감당 가능한 만큼"은 책상에서 계산만 해서는 안 나옵니다. 인스턴스 CPU/메모리, DB 스펙, 실제 데이터 분포, 작업이 섞이는 패턴이 전부 얽혀 있기 때문입니다. 부하 테스트로 직접 측정해야 했습니다.

## 4. 해결 - 두 한계에 장치를 두고, 부하 테스트로 값을 정한다

문제 ①(나가는 쪽)과 문제 ②(들어오는 쪽)은 서로 독립적이라, 장치도 두 개를 따로 세워야 합니다. 나가는 쪽은 외부 리소스마다 세마포어로 동시 호출 수를 묶고, 들어오는 쪽은 Tomcat `max-connections`로 동시에 처리 중인 요청 수를 묶습니다. 장치부터 정하고, 그 값은 부하 테스트로 확정하겠습니다.

### 4-1. 나가는 쪽 - 외부 리소스마다 세마포어를 둔다

외부 자원(푸시 서버 한도, 외부 API 동시 수용량, 우리 커넥션 풀)이 유한한 이상, 무한정 생성은 한계를 올려 주는 게 아니라 한계 아래에 줄 서는 스레드 수만 늘립니다. 그렇다고 해법이 가상 스레드를 포기하는 건 아니었습니다. 외부 리소스로 나가는 길목마다 동시에 나갈 수 있는 호출 수를 세마포어로 명시하는 것이었습니다. 세마포어는 메모리를 아끼려고 두는 게 아닙니다. 무한정 생성으로 사라진 속도 늦추라는 신호를 한 줄로 다시 세우는 장치입니다.

패턴은 두 가지로 갈립니다.

```java
// (a) 사용자 동기 경로: 짧게만 기다려 보고 안 되면 즉시 거절
if (!gate.tryAcquire(timeout)) {
    throw new TooBusyException();   // 503으로 떨어뜨리고 점유한 자원 회수
}
try { return call.get(); } finally { gate.release(); }

// (b) 배치 경로: 그냥 대기 (가상 스레드는 막혀도 OS 스레드를 안 잡으니까)
gate.acquire();
try { return call.get(); } finally { gate.release(); }
```

소셜 로그인처럼 사용자가 기다리는 경로는 (a)입니다. 짧은 시간 안에 허가를 얻지 못하면 무한정 줄 세우지 않고 바로 503으로 거절하고, 그 요청이 붙잡고 있던 처리 자원을 회수합니다. 푸시 발송이나 파싱 파이프라인처럼 사용자가 기다리지 않는 배치는 (b)입니다. 거절보다 대기가 맞고, 가상 스레드는 어차피 막히면 캐리어를 반납하니까 대기해도 OS 스레드를 낭비하지 않습니다.

`try ... finally release()`로 가상 스레드가 어떻게 끝나든(정상이든 예외든) 세마포어 허가가 반드시 반납되게 했습니다.

이렇게 외부로 나가는 모든 길목에 제한 장치를 세웠습니다. 사용자 동기 경로(소셜 OAuth)는 빠른 거절 방식으로, 푸시 발송은 적당한 동시 호출 수로 묶고 초과분은 다음 주기로 이월하는 방식으로, 스크래핑 HTTP·헤드리스 브라우저·외부 AI 파이프라인처럼 무거운 자원은 아주 작게(브라우저·AI는 사실상 직렬로) 묶었습니다. 외부 자원마다 성격이 다르니 거절/대기 정책과 동시성 값도 다르게 갑니다.

들어오는 쪽은 3장에서 봤듯 `max-connections` 하나가 유일한 입구라, 기본값 8192 대신 작은 인스턴스가 감당할 보수적인 값으로 고정했습니다. 이렇게 나가는 쪽과 들어오는 쪽 장치는 세웠지만, 세마포어 값도 `max-connections` 값도 얼마가 적정인지는 아직 못 정했습니다. 이제 그 값들을 부하 테스트로 확정할 차례입니다.

### 4-2. RPS를 계단식으로 올리고, 의도된 거절과 진짜 장애를 분리한다

이제 한계를 찾는 측정 방법입니다. 단일 부하로 "통과/실패"만 보면 한계가 어디인지 모릅니다. 그래서 k6로 RPS를 단계마다 한 칸씩 올리는 계단식 부하를 줬습니다. 동시 사용자 수(VU)가 아니라 도착률(RPS)을 직접 올린 이유는, 우리가 찾는 한계(DB 풀, 세마포어, `max-connections`)가 전부 초당 몇 개가 도착하나에 반응하는 자원이기 때문입니다. 시스템이 꺾이는 건 도착률이 처리율을 넘는 순간이라, 도착률을 직접 계단식으로 올려야 꺾이는 지점이 깨끗하게 보입니다.

측정하면서 하나는 꼭 챙겼습니다. 의도된 거절과 진짜 장애를 분리하는 것이었습니다. 우리 제한 장치는 포화되면 일부러 429/503을 돌려줍니다. 이건 보호 장치가 제대로 작동한다는 성공 신호입니다. 이걸 504나 연결 끊김 같은 진짜 장애와 같은 통에 넣어 세면, 꺾이는 지점이 안 보입니다. 그래서 결과를 네 가지로 나눠서 기록했습니다.

```js
if (2xx)        success;            // 성공
else if (429)   intendedRateLimit;  // 의도된 거절 → '에러'에서 제외
else if (503)   intendedShed;       // 의도된 거절 → '에러'에서 제외
else            realError;          // 이것만 진짜 장애
```

429/503을 '에러'에서 분리한 이 처리 덕분에, 나중에 디버깅할 때 찾아볼 범위가 확 줄었습니다. "에러가 났다"가 아니라 "어느 장치가 거절했나(외부 세마포어인가, DB 커넥션 대기 타임아웃인가, 진짜 5xx인가)"를 바로 구분할 수 있기 때문입니다.

### 4-3. 측정 결과 - 들어오는 한계는 버텼고, 한 층 안쪽이 터졌다

먼저 본 건 "제한 장치를 작게 깔았을 때 목표 트래픽을 안전하게 받는가, 못 받으면 어느 층이 먼저 무너지는가"였습니다. 실제 트래픽 비중이 높은 경로 몇 개를, 제한 장치를 일부러 작게 깔고 돌렸습니다.

읽기 경로들은 작은 풀에서도 0 에러로 버텼습니다. DB 읽기 풀을 일부러 작게 깔았는데도 커넥션 대기가 쌓이는 신호가 한 번도 안 떴고, 부하를 올리는 동안 Tomcat 입구에서 끊긴 요청도 없었습니다. 들어오는 한계(`max-connections`)는 이 보수적인 값에서 한 번도 거절을 안 했다는 뜻입니다.

문제는 쓰기 경로(소셜 로그인)였습니다. 유일한 동기 외부 I/O 경로입니다. 외부 변동성을 없애려고 OAuth 호출은 고정 지연 mock으로 뒀는데, 그게 일정 시간 park한 뒤 사용자 저장 + 토큰 저장이 따라옵니다. 부하를 올리니 실패율이 크게 튀었고, 실패 응답이 한 시점에 뚜렷하게 몰렸습니다. 원인은 세 가지 단서로 좁혔습니다.

- **① 제한 장치 거절이 아니다.** 의도된 거절(429/503) 카운터가 모두 0이라, 외부 세마포어가 거절한 요청은 한 건도 없었습니다. 나가는 쪽 한계는 범인이 아니었습니다.
- **② 실패가 몰린 시점이 가리킨다.** 실패 응답이 DB 커넥션 획득 타임아웃 값에 오버헤드를 더한 시점에 정확히 몰렸습니다. 요청이 OAuth park를 끝내고 DB 커넥션을 잡으러 갔다가, 풀이 안 비어서 타임아웃까지 기다린 뒤 획득 실패로 떨어진 것입니다.
- **③ 계산해 봐도 같은 곳을 가리킨다.** 소셜 로그인은 OAuth park 구간을 `@Transactional` 안에서 타서 커넥션 보유 시간이 사실상 요청 전체입니다. 리틀의 법칙(Little's Law)으로 `풀 크기 / 보유 시간`을 계산하면 성공 처리량 상한이 나오는데, 측정치와 자릿수·방향이 같았습니다.

세 단서가 전부 같은 곳을 가리켰습니다. 이 부하에서 당장 터진 건 외부 세마포어가 아니라 DB 쓰기 풀이었습니다. 3장에서 개념으로만 말했던 "외부를 막아도 한 층 안쪽에 한계가 남는다"가 부하 테스트에서 그대로 재현된 것입니다. 그렇다고 외부 세마포어는 멀쩡했다는 뜻은 아닙니다. 나가는 쪽 세마포어 값도, 안쪽 DB 쓰기 풀 크기도 결국 이 서버·DB 인스턴스가 감당 가능한 범위에 맞춰야 하는 값이라, 둘 다 인스턴스 스펙에 맞게 조정했습니다. 당장 실패를 만든 쓰기 풀은 DB 인스턴스에 맞춰 키워 다시 돌리니 실패가 0으로 떨어졌고, 외부 세마포어 값들도 서버와 외부 자원 한도에 맞춰 같이 정리했습니다. 이 구간에서도 Tomcat 입구 거절은 0이었고, 거절은 전부 DB 커넥션 대기에서 났습니다.

의도된 거절 카운터가 0이라는 것 하나가 제한 장치 거절이 아님을 바로 확정해 줘서, 곧장 응답 지연이 몰린 구간으로 눈을 돌릴 수 있었습니다. 4-2에서 의도된 거절과 진짜 장애를 분리해 둔 게 여기서 디버깅 범위를 좁혀 준 셈입니다.

### 4-4. 확정한 값과, 이 측정이 입증한 범위

이 측정이 수치로 직접 고정해 준 건 두 가지입니다.

- **DB 쓰기 풀 크기**: 실패가 커넥션 타임아웃 시점에 몰렸고, 의도된 거절이 0이라 외부 제한 장치를 배제할 수 있었습니다. DB 인스턴스가 감당 가능한 만큼으로 풀을 키우니 실패가 사라졌습니다.
- **Tomcat `max-connections`**: 기본값(8192)은 작은 인스턴스에선 위험하므로, 서버·DB 스펙에 맞춰 보수적인 값으로 조정했습니다. 측정한 모든 경로에서 입구 레벨 거절이 0이라 이 값으로 충분했고, 부하가 더 커지면 더 낮출 여지도 남겨 뒀습니다.

이게 안으로 들어오는 한계(문제 ②)의 확정입니다. 밖으로 나가는 한계(문제 ①)의 세마포어 값들은 따로 정했습니다.

여기서 이 측정이 무엇을 입증했고 무엇은 안 했는지 솔직하게 적어 둡니다. 한 번의 측정으로 모든 값이 다 검증됐다고 말하면 과장입니다.

- 소셜 로그인 경로는 부하 테스트에서 실제로 밀렸고, 그때 범인이 외부 세마포어가 아니라 DB 쓰기 풀이라는 게 의도된 거절 0으로 드러났습니다. 즉 그 부하에서 외부 세마포어 값이 거절을 만들 만큼 빡빡하지 않았다는 게 부수적으로 확인된 셈입니다.
- 푸시 발송, 스크래핑, 브라우저, 파싱 세마포어 값은 이 경로 측정에 포함되지 않았습니다. 이 값들은 각자 자기 경로를 포함한 별도 측정과, 상대 자원의 한도(외부 AI/푸시 서버 호출 한도, 브라우저 메모리)를 그대로 베껴 적는 보수 산정으로 정했습니다. 이번 측정이 정당화해 주는 숫자가 아닙니다.

정리하면, 안으로 들어오는 한계(`max-connections`, 쓰기 풀)는 RPS를 올려 가며 직접 측정해 확정했고, 밖으로 나가는 한계(세마포어)는 경로별로 측정/산정했습니다. 결국 책상에서 계산한 값이 아니라 부하 테스트로, 외부 세마포어와 DB 쓰기 풀·`max-connections`를 모두 서버·DB 인스턴스 스펙에 맞게 정한 것입니다.

## 5. 회고

### 5-1. 가상 스레드는 효율을 끌어올렸지만, 그 대가로 리소스를 보호하는 법을 배웠다

이 서비스는 본질적으로 I/O가 많은 서비스입니다. 혜택 조회는 DB I/O이고, 소셜 로그인은 외부 OAuth I/O이고, 스크래핑·파싱·푸시 발송은 전부 외부 네트워크 I/O입니다. 이런 환경에서 가상 스레드의 이점은 분명했습니다. 블로킹 I/O 동안 OS 스레드를 붙잡아 두는 낭비를 없애서, 같은 하드웨어로 훨씬 많은 동시 I/O를 소화할 수 있었습니다.

그런데 그 효율에는 대가가 따릅니다. 블로킹 대기를 없앤다는 건 그 대기가 알아서 해 주던 속도 조절까지 같이 없앤다는 뜻입니다. 이번 트러블슈팅은 그 개념을 부하 테스트에서 실제 값으로 확인하고, 비워진 속도 조절을 세마포어와 `max-connections`로 어디까지 다시 세워야 하는지를 직접 정한 작업이었습니다. 효율을 얻은 만큼 손이 더 가는 일이 한 세트로 따라온다는 걸, 개념이 아니라 실제 숫자로 마주한 셈입니다.

### 5-2. 사실 이건 가상 스레드만의 문제는 아니다

한 가지 짚고 넘어가자면, 서버/DB 인스턴스가 감당 가능한 한계를 측정해야 한다는 문제 자체는 가상 스레드만의 문제가 아닙니다. 플랫폼 스레드 풀 방식이었어도 "이 인스턴스가 초당 몇 RPS까지 버티나"는 똑같이 측정해야 했을 숙제입니다. 부하 테스트로 인스턴스 가용량을 확인하는 건 스레드 모델과 무관한, 모든 백엔드의 기본기입니다.

다만 해법의 형태는 달랐을 수 있습니다. 플랫폼 스레드 풀 방식은 풀과 블로킹 I/O 덕분에 자체적으로 보호되는 구조입니다. 스레드 풀 크기 N이 곧 "동시에 외부를 두드릴 수 있는 작업 수"의 상한이고, 작업이 블로킹 I/O에서 대기하면 그 스레드가 점유된 채 막혀서 자연스럽게 속도가 조절됩니다. 즉 플랫폼 스레드 풀에서는 풀 크기 하나가 들어오는 요청 제한과 나가는 호출 제한을 동시에 해 줬습니다. 이번처럼 Tomcat `max-connections`와 외부 세마포어를 따로 세우는 방식이 아니라, 풀 크기 한 줄로 끝났을 수도 있다는 뜻입니다.

가상 스레드는 그 풀 하나가 두 가지를 동시에 해 주던 자기 보호 구조를 해체합니다. 그래서 보호 장치를 나가는 쪽(세마포어)과 들어오는 쪽(`max-connections`)으로 나눠서 따로 세워야 했습니다. 개념으로만 알던 "어디까지 모델이 막아 주고 어디서부터 내가 막아야 하는가"의 경계가, 이번에 부하 테스트에서 구체적인 값으로 손에 잡혔습니다. 플랫폼 스레드를 썼다면 그 경계가 풀 크기 안에 숨어서 안 보였을 텐데, 가상 스레드를 쓰면서 그 경계를 직접 마주하게 된 셈입니다.

## 마치며: 왜 Kotlin/Go가 아니라 자바 가상 스레드였나

I/O가 많은 동시성을 잘 다루는 선택지는 많습니다. 코틀린 코루틴, Go의 고루틴, 리액티브 스택, 전부 이 문제를 우아하게 풉니다. 여기서는 "그 가상 스레드를 왜 *자바*로, 즉 코틀린/Go가 아니라 자바 가상 스레드로 골랐나"만 짧게 적겠습니다. 더 빨라서도, 더 트렌디해서도 아닙니다.

개인적인 생각이지만, 개발자의 일상 대부분은 신규 개발이 아니라 유지보수와 레거시 관리라고 봅니다. 그리고 현실의 수많은 백엔드는 자바로 짜여 있고, 앞으로도 한동안 자바로 관리될 것입니다. 가상 스레드의 가장 큰 미덕은 성능 수치가 아니라 호환성이라고 느꼈습니다. 언어를 안 바꾸고(같은 자바), 무엇보다 기존 애플리케이션의 블로킹 I/O 스타일 코드를 그대로 둔 채 옮겨 갈 수 있습니다. `Socket.read()`, JDBC, 동기 HTTP 호출을 콜백이나 코루틴으로 다시 쓰지 않고, 설정 한 줄(`spring.threads.virtual.enabled=true`)로 같은 코드가 논블로킹의 이점을 받습니다.

이 이점이 어디서 나오는지 보면, JDK가 `Socket.read()` 같은 블로킹 호출을 내부에서 가로채 리눅스 기준으로는 epoll에 등록해 두고, 가상 스레드를 캐리어에서 내려놓습니다. 응답이 준비되면 다시 올려 이어 실행합니다. 그래서 코드는 블로킹처럼 위에서 아래로 읽히지만, 실제 I/O는 논블로킹으로 처리됩니다.

다만 이 호환성에는 오랫동안 조건이 하나 있었습니다. `synchronized` 블록 안에서 블로킹하면 가상 스레드가 캐리어에 고정되어(피닝) 내려오지 못했습니다. 그래서 한동안은 라이브러리들이 `synchronized`를 `ReentrantLock`으로 바꿔 피닝이 생기는 지점을 걷어내야 했습니다. 이 문제는 JDK 24에서 대부분 해소됐습니다. `synchronized` 블로킹이 더 이상 캐리어를 붙잡지 않게 되면서, 기존 코드를 그대로 옮겨 와도 피닝을 걱정할 일이 크게 줄었습니다. 이제 남은 피닝은 native 메서드(JNI) 호출 정도라, 일반적인 애플리케이션 코드에서는 거의 마주칠 일이 없습니다.

JDBC나 기존 Spring 스택의 동기 API가 '가상 스레드를 지원한다'는 말도 이 맥락입니다. 논블로킹으로 새로 짠 게 아니라, 밑단이 결국 `Socket` I/O라 위에서 말한 가로채기가 그대로 적용되고, 드라이버와 라이브러리들도 피닝을 유발하던 코드를 걷어냈습니다. 그래서 기존 동기 API 코드를 그대로 두고도 가상 스레드 위에서 문제없이 돌아갑니다.

기존 자바 자산을 들고 가야 하는 입장에서 이 마이그레이션 비용 차이는 큽니다. 그래서 이번 신규 프로젝트에 먼저 적용해 보고, 이렇게 트러블슈팅까지 부딪혀 본 것입니다.

물론 이건 어디까지나 한 명의 기술 선택 근거입니다. 실무에서는 팀 컨벤션, 기존 스택, 팀원 숙련도에 따라 기술이 정해질 것입니다. 코틀린 코루틴에 익숙한 팀이라면 그게 더 나은 선택일 수 있습니다. 다만 "왜 가상 스레드냐"고 누가 물으면, 저는 이제 "기존 자바 코드를 블로킹 스타일 그대로 들고 갈 수 있는 호환성"을 첫 번째 이유로 답할 수 있게 됐습니다. 그리고 그 호환성을 실제로 누리려면 이 글에서 다룬 사이징 작업이 한 세트로 따라온다는 것까지 알고 쓰는 것과 모르고 쓰는 건 분명히 다르다고 생각합니다. 이번 트러블슈팅으로 그걸 몸으로 배웠습니다.
