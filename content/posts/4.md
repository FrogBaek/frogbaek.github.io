## 들어가며

이 글은 Java 25 Virtual Thread를 새 개인 프로젝트에 처음부터 올려놓고 설계하면서 마주친 문제들과, **같은 워크로드를 플랫폼 스레드와 가상 스레드 두 모드로 로컬에서 나란히 돌려 본 비교 실험**을 정리한 글입니다. Virtual Thread의 내부 동작 원리(JVM이 blocking API를 non-blocking으로 변환하는 메커니즘, M:N 스레딩 모델에서의 동기화 등)는 이 글의 범위를 벗어나므로, 이론은 [가상 스레드는 어떻게 I/O를 처리하는가 - blocking API의 내부 동작 원리]({{< ref "3.md" >}}) 글에, 그 원리를 C로 바이트 단위까지 직접 구현해 본 저수준 실습은 [가상 스레드는 어떻게 동작하는가 - C로 직접 구현해 보기]({{< ref "2.md" >}}) 글에 따로 두었습니다.

프로젝트는 통신사/카드사 혜택 정보를 자동 수집하고 AI로 파싱하여 사용자에게 전달하는 Spring Boot 백엔드입니다. Tomcat 요청 처리, 다수의 스케줄러, 알림 병렬 발송, 브라우저 자동화가 동시에 동작하는 환경이라 동시성 요구가 높았습니다.

한 가지 미리 선을 그어 둡니다. **이 글의 측정 숫자는 전부 로컬입니다.** 스레드 모델 차이만 분리해 보려고 병목이 아닌 쪽을 전부 눌러 둔 환경이라, 여기서 나온 값은 모드 비교용이지 운영에서 쓸 사이징 값이 아닙니다. 운영과 동일 스펙, 마스킹 DB 위에서 외부 세마포어와 Tomcat `max-connections`의 실제 값을 어떻게 확정했는지(무한정 생성이 만든 리소스 한계를 운영 인프라에서 실측해 막은 트러블슈팅)는 [“가상 스레드는 마음껏 만들어도 된다”, 운영에서 곧이곧대로 믿으면 생기는 일]({{< ref "5.md" >}}) 글에서 다룹니다.

## 1. 가상 스레드 기본 설정

최신 Spring Boot에서는 설정 한 줄로 끝납니다.

```yaml
spring:
  threads:
    virtual:
      enabled: true
```

이 플래그 하나로 **Tomcat worker 스레드, `@Async`, Spring Modulith 이벤트 리스너, `@Scheduled` 메서드**가 모두 가상 스레드 위에서 실행됩니다. 스케줄러도 자동 구성이 `SimpleAsyncTaskScheduler`를 가상 스레드 모드로 띄워 주기 때문에 별도 작업이 필요 없습니다.

애플리케이션 단에서 추가로 건드려야 하는 건, 가상 스레드 자체가 아니라 그 위에서 살아남아야 하는 **컨텍스트 전파와 에러 처리** 쪽입니다. 다음 장부터는 그 이야기입니다.

## 2. ThreadLocal을 ScopedValue로 전환한 이유

### 2-1. ThreadLocal의 문제

이 프로젝트에서는 두 가지 컨텍스트를 스레드 단위로 관리해야 했습니다.

- **요청 ID**: 로그 추적용 (nginx → 앱 → 로그)
- **인가 주체**: 누가 이 요청/작업을 실행하는가 (소셜 회원, 게스트, 관리자, 시스템)

ThreadLocal로 이걸 관리하면 Virtual Thread 환경에서 두 가지 문제가 생깁니다.

1. **대량 생성 시 메모리 부담**: `ThreadLocalMap` 자체는 지연 생성이라 `set()`이 호출되기 전에는 없습니다. 그런데 한 번이라도 `set()`이 호출된 가상 스레드는 수명이 끝날 때까지 그 Map을 들고 있습니다. 플랫폼 스레드 풀은 스레드 수가 제한적이라 살아있는 Map 수도 자연히 제한되지만, 요청마다 새로 만들어지는 가상 스레드 환경에서는 `set()`을 호출하는 경로가 많을수록 *동시 가상 스레드 수 × 보관 엔트리 수* 만큼 Map이 동시에 살아있게 됩니다. `InheritableThreadLocal`로 자식 스레드에 전파하면 복사 비용까지 더해져 부담이 더 커집니다.
2. **스코프가 구조적으로 강제되지 않음**: ThreadLocal은 `set()`과 `remove()`를 개발자가 직접 호출해야 합니다. 예외 경로에서 `remove()`가 누락되거나, 중첩 호출에서 이전 값이 의도치 않게 덮어씌워지는 버그가 나기 쉽습니다.

### 2-2. ScopedValue로 전환

Java 25에서 정식 기능이 된 ScopedValue는 이 두 가지 문제를 해결합니다. 값이 불변(immutable)이고, 블록 스코프가 끝나면 자동으로 해제되므로 `remove()` 누락 자체가 불가능합니다.

**요청 ID 바인딩:**

```java
public final class RequestScope {
  public static final ScopedValue<String> REQUEST_ID = ScopedValue.newInstance();
}
```

```java
public class RequestIdFilter extends OncePerRequestFilter {

  @Override
  protected void doFilterInternal(HttpServletRequest req,
      HttpServletResponse res, FilterChain chain) {
    String requestId = resolveRequestId(req);

    ScopedValue.where(RequestScope.REQUEST_ID, requestId)
        .call(() -> {
          chain.doFilter(req, res);
          return null;
        });
  }
}
```

**인가 컨텍스트 바인딩:**

```java
public final class AuthorizationContextHolder {
  static final ScopedValue<AuthorizationActor> CONTEXT = ScopedValue.newInstance();

  public static AuthorizationActor getActor() {
    return CONTEXT.isBound() ? CONTEXT.get() : null;
  }

  public static <T> T callAs(AuthorizationActor actor, Callable<T> action) {
    return ScopedValue.where(CONTEXT, actor).call(action);
  }
}
```

`ScopedValue.where().call()` 블록이 끝나면 자동으로 이전 바인딩이 복원됩니다. `remove()`를 잊어버릴 일 자체가 없습니다.

### 2-3. MDC도 ScopedValue로 대체

로그에 요청 ID를 찍기 위해 보통 MDC(ThreadLocal 기반)를 쓰지만, 이것 역시 ThreadLocal이라는 점은 동일합니다. 이 프로젝트에서는 로깅 프레임워크 레벨의 커스텀 컨버터를 하나 두고 **ScopedValue에서 직접 읽어 로그 필드로 꽂도록** 해서, MDC 경유 없이 같은 결과를 냅니다. 이 한 번의 치환으로 애플리케이션 코드에서 ThreadLocal 기반 MDC 호출이 전부 사라졌습니다.

## 3. 스케줄러와 이벤트 리스너의 인가 문제

### 3-1. HTTP 요청 없이 실행되는 코드

스케줄러와 이벤트 리스너는 HTTP 요청 컨텍스트 없이 실행됩니다. 필터를 거치지 않으니 ScopedValue에 인가 주체가 바인딩되지 않습니다.

그런데 이 코드들도 내부적으로 인가가 필요한 서비스를 호출합니다. FCM 알림 발송 스케줄러가 사용자 데이터를 조회하려면, "시스템 작업이 실행 중"이라는 컨텍스트가 있어야 합니다.

### 3-2. @RunAsSystem

이 문제를 `@RunAsSystem` 커스텀 어노테이션과 AOP로 해결했습니다.

```java
@Aspect
public class SystemPrincipalAspect {

  @Around("@annotation(runAsSystem)")
  public Object runAsSystem(ProceedingJoinPoint pjp, RunAsSystem runAsSystem) {
    return AuthorizationContextHolder.callAs(
        AuthorizationActor.system(runAsSystem.value()), pjp::proceed);
  }
}
```

사용하는 쪽에서는 어노테이션 하나만 붙이면 됩니다.

```java
@RunAsSystem("PENDING_NOTIFICATION_SENDER")
@Scheduled(...)
public void dispatchPendingNotifications() {
  // 이 메서드 안에서 AuthorizationContextHolder.getActor() == system("PENDING_NOTIFICATION_SENDER")
}
```

작업별로 이름을 다르게 지정하면 로그에서 어떤 시스템 작업이 실행되었는지 식별할 수 있습니다.

## 4. JDK 24+에서는 synchronized pinning이 사라졌다

### 4-1. pinning이 문제였던 시절

JDK 23 이전에는 Virtual Thread가 `synchronized` 블록 안에서 I/O를 만나면 carrier thread에서 unmount되지 못하는 **pinning** 문제가 있었습니다. carrier가 모니터를 잡고 있는 동안 다른 가상 스레드도 그 carrier를 쓰지 못했고, 사실상 platform thread 한 개가 통째로 묶였습니다.

당시 흔한 우회책은 `synchronized`를 쓰는 라이브러리 호출만 별도의 플랫폼 스레드 풀에 격리해서 carrier가 묶이는 걸 막는 것이었습니다. 가상 스레드를 쓰는 코드 한쪽에 "이 호출만 OS 스레드로 빼낸다"는 구조가 섞여 있는 건 그리 달갑지 않은 형태입니다.

### 4-2. JEP 491이 근본적으로 해결했다

JDK 24의 [JEP 491 — Synchronize Virtual Threads without Pinning](https://openjdk.org/jeps/491)이 이 문제를 해결합니다. **`synchronized` 블록 안에서도 Virtual Thread가 carrier thread에서 정상적으로 unmount**되고, `Object.wait()` 역시 carrier를 잡지 않습니다.

이 프로젝트는 처음부터 JDK 25를 썼기 때문에 격리용 플랫폼 스레드 풀을 따로 만들어 둘 일 자체가 없었습니다. 내부에 `synchronized` 블록을 끼고 있는 라이브러리 호출도 다른 코드와 동일하게 가상 스레드 위에서 직접 실행됩니다. 동시성 제한이 필요한 자리에는 풀 격리 대신 `Semaphore` 한 줄만 둡니다.

```java
concurrencyLimit.acquire();
try {
  return doWork();
} finally {
  concurrencyLimit.release();
}
```

> **JDK 23 이하에서 올라오는 프로젝트라면, pinning 우회용으로 만들어 둔 platform thread 격리 코드가 어딘가 남아 있는지 점검해 볼 것을 권합니다.** JDK 24+에서는 이 코드가 불필요해지므로 그대로 둘 이유가 없습니다.

### 4-3. JEP 491이 해결하지 않은 한 가지: 자식 스레드 컨텍스트 전파

ScopedValue는 같은 가상 스레드 안에서는 그대로 유지되지만, **`ExecutorService`로 새 스레드를 만드는 순간 전파되지 않습니다.** 교과서적인 답은 `StructuredTaskScope`로 부모-자식 관계를 명시적으로 묶는 것이고, 이렇게 하면 ScopedValue가 자동 전파됩니다. 그런데 `StructuredTaskScope`는 JDK 25 기준으로 아직 **preview**입니다 ([JEP 505](https://openjdk.org/jeps/505)). preview API를 운영 코드에 박는 건 부담스러워서 이 프로젝트에서는 쓰지 않았고, 대신 일반 `ExecutorService`를 쓰면서 **부모 컨텍스트를 직접 캡처해 자식에서 다시 바인딩**하는 래퍼를 만들었습니다.

이 프로젝트에서는 FCM 알림 발송 스케줄러가 `newVirtualThreadPerTaskExecutor()`로 수백 개의 자식 가상 스레드를 동시에 생성합니다. 부모 스케줄러의 인가 컨텍스트(`@RunAsSystem`으로 바인딩된 값)와 요청 ID가 자식에 전달되어야 하므로, 아래와 같은 얇은 propagator 하나를 둡니다.

```java
public final class VirtualThreadContextPropagator {

  public static <T> Callable<T> propagate(Callable<T> task) {
    // 부모에서 지금 바인딩된 값을 캡처
    AuthorizationActor actor = AuthorizationContextHolder.getActor();
    String requestId = RequestScope.REQUEST_ID.isBound()
        ? RequestScope.REQUEST_ID.get() : null;
    // 자식에서 다시 바인딩
    return () -> AuthorizationContextHolder.callAs(actor,
        () -> ScopedValue.where(RequestScope.REQUEST_ID, requestId).call(task::call));
  }
}
```

```java
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
  for (var task : dispatchTasks) {
    executor.submit(VirtualThreadContextPropagator.propagate(task));
  }
}
```

같은 가상 스레드 안에서 일을 끝까지 처리하는 경로(예: 단일 HTTP 요청)에는 ScopedValue가 그대로 유지되니 이 래퍼가 필요 없습니다. **자식 스레드를 명시적으로 만드는 경로에서만** 필요한 패턴입니다. `StructuredTaskScope`가 정식 API로 승격되는 시점에는 이 래퍼도 지우고 갈아탈 예정입니다.

## 5. 측정 준비

### 5-1. 답하고 싶었던 질문

제가 먼저 답하고 싶었던 질문은 이것입니다.

> **같은 일을 시키면 플랫폼 스레드와 가상 스레드가 뭐가 다른가?**

한 가지는 먼저 분명히 해 둡니다. 이 글의 숫자는 전부 로컬 측정입니다. 운영 환경과는 아키텍처가 다르기 때문에 **스레드 모델 차이를 분리해 보기 위한 데이터**일 뿐이고, reactive/WebFlux 같은 프로그래밍 모델 비교나 순간적인 부하 스파이크 응답 같은 주제는 이 실험으로 답할 수 없어 다루지 않습니다.

### 5-2. 측정 환경

측정에 영향을 주는 항목만 추립니다.

| 항목 | 값 |
|---|---|
| JDK / GC | JDK 25, G1, `-Xmx3g -Xms3g` |
| 활성 코어 | `-XX:ActiveProcessorCount=4` (앱 / 부하 도구 / DB / mock을 각각 다른 코어에 핀) |
| Tomcat max threads | 측정별로 명시 (200 / 400 / 800) |
| HikariCP write / read pool | 200 / 200 |
| OAuth mock 지연 | 1,500ms |
| 부하 도구 | k6 |
| 자원 모니터링 | Spring Boot Actuator 1Hz polling |

CPU를 네 구역으로 나눈 이유는 하나입니다. **앱 / 부하 도구 / DB / mock이 같은 코어를 공유하면 측정 노이즈와 스레드 모델 효과가 섞입니다.** 측정 변수만 남기기 위해 가능한 간섭원을 전부 격리했습니다.

mock OAuth의 1.5초 지연은 실제 외부 응답보다 길지만, **외부 호출이 길어졌을 때 어떤 일이 일어나는지를 보기 위한 의도적 상한 시나리오**입니다. 실제 응답이 더 짧다면 효과의 절대 크기는 그만큼 작아집니다.

### 5-3. 워크로드

트래픽을 두 경로로 반씩 섞었습니다.

- **소셜 로그인 (50 %)**: 외부 OAuth를 mock으로 1.5초 park한 뒤 사용자 upsert + refresh token insert로 이어지는 **외부 I/O 블로킹 경로**. write-pool 사용.
- **게스트 탐색 (50 %)**: 로컬 캐시에 대부분 적중해 거의 즉시 응답하는 **캐시 히트 경로**. read-pool 사용.

부하 패턴은 웜업 30초(VU 20) → 램프 15초 → **목표 VU 유지 180초** → 쿨다운 10초이며, 목표 VU는 측정마다 200 / 400 / 800으로 바꿉니다(아래 6-3절). 여기서 VU(Virtual User, 가상 사용자)는 부하 도구가 동시에 흉내 내는 가상 사용자 수를 뜻합니다.

## 6. 오해를 측정으로 무너뜨리기

### 6-1. 흔히 듣는 이야기 두 가지

가상 스레드 도입을 고민할 때 흔히 따라붙는 이야기는 대체로 이런 두 가지로 모입니다.

1. **"처리량이 크게 늘어난다."** Tomcat 기본 설정 그대로 둔 서버에 플랫폼/가상 모드를 나란히 놓고 돌려 보면 가상 쪽 rps가 몇 배로 뛴다는 식의 비교입니다. 자주 인용되는 수치는 그때그때 다른데(2배, 4배, 한 자리 배수 전반), 공통점은 **플랫폼 모드가 기본 Tomcat 풀 그대로 측정됐다**는 점입니다.
2. **"경량이니 마음껏 만들어도 된다."** 생성 비용이 힙 할당 수준이니 풀도 Semaphore도 없이 필요할 때마다 그냥 `Thread.ofVirtual().start(task)` 하면 된다는 주장입니다.

두 이야기 모두 일부 조건에서는 맞고, 일부 조건에서는 측정으로 간단히 무너집니다. 문제는 그 경계가 어디고, 그 바깥에서는 가상 스레드가 뭘 해 주는지입니다. 이 장은 Tomcat 풀을 부하에 맞춰 키운, 단일 변수 비교의 정도를 지킨 측정으로 두 이야기를 하나씩 맞춰 보고, 마지막에 "그럼 진짜 차이는 어디에 있느냐"로 넘어갑니다.

### 6-2. 측정 설계

가상 스레드를 둘러싼 흔한 비교들의 공통점은 **Tomcat 풀이 부하 대비 작았다**는 것입니다. 그 쪽에 공정한 풀 크기를 주고 나서야 두 모드를 나란히 놓을 수 있습니다.

같은 워크로드, 같은 HikariCP 200 / 200, 같은 MySQL 설정. 다른 점은 두 가지뿐입니다.

- **플랫폼 스레드 모드**: `-Dserver.tomcat.threads.max=<VU와 동일>` (매 측정마다 부하 크기에 맞춰 올립니다)
- **가상 스레드 모드**: `-Dspring.threads.virtual.enabled=true`

### 6-3. 결과표

VU를 200 / 400 / 800 세 단계로 올려가며 두 모드를 측정했습니다.

| VU | 모드 | Tomcat | 처리량(rps) | p95 | 에러율 | OS 스레드 | vol/s | nonvol/s | 총 switch/s |
|---|---|---|---|---|---|---|---|---|---|
| 200 | 플랫폼 | 200 | 252.2 | 1,642ms | 0 | 249 | 3,217 | 1,324 | 4,541 |
| 200 | 가상 | — | 254.5 | 1,646ms | 0 | 49 | 5,659 | 783 | 6,442 |
| 400 | 플랫폼 | 400 | 497.6 | 1,705ms | 0 | 449 | 5,853 | 7,168 | 13,021 |
| 400 | 가상 | — | 494.2 | 1,719ms | 0 | 49 | 7,017 | 1,670 | 8,687 |
| 800 | 플랫폼 | 800 | (HikariCP 포화) | — | 47.6% | 847 | — | — | — |
| 800 | 가상 | — | (HikariCP 포화) | — | 31.3% | 49 | — | — | — |

표의 용어를 먼저 풀면, p95는 응답시간 상위 95퍼센타일(느린 쪽 5%를 제외한 값), vol/s는 초당 자발적 컨텍스트 스위치, nonvol/s는 초당 비자발적 선점입니다. vol과 nonvol의 차이는 6-8절에서 자세히 다룹니다.

VU 800 행은 양쪽 모두 HikariCP 상한에 걸려 정상 상태 측정이 아닙니다. 이후 자원 컬럼(OS 스레드, 컨텍스트 스위치)도 정상 상태 구간에서만 의미가 있어 VU 200과 400을 기준으로 읽습니다.

이 표를 앞에 두고, 먼저 앞서 꺼낸 두 이야기(처리량, 무제한 생성)를 맞춰 본 뒤, 측정 중에 드러난 부수적 관찰 하나를 짚고, 마지막으로 처리량 컬럼이 아니라 자원 컬럼 쪽에서 실제 차이가 어디에 있는지를 읽어 봅니다.

### 6-4. 오해 ① - "처리량이 크게 늘어난다"

결과표의 첫 네 줄(VU 200과 400)이 이 오해를 그대로 반박합니다. **Tomcat 풀을 부하(VU)와 같은 크기로 맞춘 뒤** 비교하면 처리량은 252.2 vs 254.5 rps, 497.6 vs 494.2 rps로 측정 오차 안이고, 유의미한 차이가 없습니다.

그럼 "몇 배" 같은 숫자는 어디서 나왔던 걸까요? Little's Law로 산수를 해 보면 바로 드러납니다. 워크로드는 두 경로로 나뉩니다. 소셜 로그인(50%)은 mock 지연 1.5초가 워커를 1.5초 동안 점유하고, 게스트 탐색(50%)은 캐시 적중이라 워커 점유가 수 ms 수준입니다. 실질적으로 Tomcat 워커를 잡는 건 소셜 경로뿐이라 플랫폼 스레드 상한은 `(Tomcat_max / 1.5s) / 0.5`, 가상 스레드는 워커 제약이 사라져 `(VU / 1.5s) / 0.5`입니다. 두 상한의 비율은 정확히 `VU / Tomcat_max`이고, Tomcat 기본값 200에 VU 400을 주면 2배, VU 800이면 4배, VU 1,600이면 8배가 나옵니다. 바꿔 말하면 **이 "배수"는 가상 스레드의 고유 성능이 아니라 그날 누가 얼마나 큰 부하를 줬는지, Tomcat을 얼마나 작은 채로 뒀는지에 따라 임의로 정해지는 비율**입니다. 블로그마다 배수가 달랐던 것도 같은 이유입니다.

정리하면 "처리량이 크게 는다"는 얘기는 결국 **부하에 비해 작은 Tomcat 풀에서 생긴 큐잉**을 보고 있었던 것이고, 풀을 부하에 맞춰 키우면 사라집니다. 운영 동시성이 풀의 절반 이하에 머문다면 가상 스레드를 켜도 측정 가능한 처리량 차이는 거의 없다는 뜻이기도 합니다.

### 6-5. 오해 ② - "경량이니 마음껏 만들어도 된다"

`Thread.ofVirtual().start(task)`가 싸니까 풀도, 세마포어도, 큐 경계도 필요 없다는 주장입니다. **생성 비용만 보면 맞습니다.** 가상 스레드 생성은 힙 객체 할당 수준이고, 이 프로젝트의 실측에서도 VmRSS(프로세스가 실제 점유한 물리 메모리)는 두 모드가 거의 같았습니다. 문제는 "만드는 순간"이 아니라 **만들어진 뒤**입니다. 이 축은 앞선 결과표에 컬럼으로 잡히지 않아 따로 꺼내 읽어야 합니다.

이 프로젝트가 실제로 부딪히거나 의식해서 피해 간 반례가 둘 있습니다.

**1. park된 가상 스레드는 힙에 continuation을 쥐고 있다.**
가상 스레드의 "경량"은 OS 스레드의 고정 스택(보통 1MB 전후)과 비교한 **상대적** 표현입니다. park 상태의 가상 스레드는 OS 스레드 하나를 점유하지 않지만, 대신 그 시점의 스택 프레임 체인을 **continuation 객체로 힙에 보관**합니다. 깊은 콜스택을 가진 채 park된 가상 스레드가 수만 개면, 그만큼 힙이 고정적으로 점유되고 young-gen GC가 돌 때마다 살아 있는 continuation 체인을 훑어야 합니다. "경량이라 무제한"은 **park 시간이 짧고 콜스택이 얕은 워크로드**에서만 체감적으로 성립합니다. 이 프로젝트의 FCM 발송처럼 외부 응답을 park된 채 오래 기다리는 경로에서는, 동시 park 수를 의식적으로 제한하지 않으면 GC/힙 쪽 비용이 조용히 축적됩니다.

**2. 무제한 생성은 속도 조절 신호를 잃는다.**
둘 중 더 중요한 반례입니다. 경계가 있는 스레드 풀은 작업 상한을 넘으면 큐가 차고, 큐가 차면 작업을 넣는 쪽이 거절당하거나 막힙니다. 이 거절/막힘이 곧 "지금은 더 못 받는다"는 신호이고, 보내는 쪽이 그 신호를 즉시 받아 속도를 줄이게 됩니다. `Thread.ofVirtual().start(task)`를 무제한으로 호출하면 이 구조가 사라집니다. 작업은 전부 즉시 받아들여지고, 대신 압력은 조용히 다음 단계(DB 풀 획득 대기, 외부 API 호출 한도, 힙, GC)로 밀려갑니다. 보내는 쪽은 받는 쪽이 포화됐다는 걸 응답 지연이 폭증하거나 OOM이 나고 나서야 뒤늦게 알게 되고, 그때는 이미 복구가 비싼 상태입니다. 이 프로젝트의 FCM 발송 경로에 `Semaphore` 한 줄을 둔 진짜 이유는 "메모리 절약"이 아니라 **스케줄러가 받는 쪽 포화를 즉시 느끼게 하기 위해서**입니다. 한 줄짜리 세마포어가 사라진 그 신호를 대신 세워 줍니다.

가상 스레드의 생성 비용이 싸다는 사실은 "풀, 세마포어, 큐 경계를 전부 없애도 된다"를 의미하지 않습니다. 경계의 역할이 바뀔 뿐입니다. CPU/메모리 절약에서 **속도 조절 신호 유지와 파킹 수명 동안 쌓이는 힙 점유의 상한 설정**으로 바뀌는 것입니다. 이 프로젝트가 가상 스레드를 쏟아내는 경로마다 세마포어로 상한을 걸어둔 건 그래서입니다.

### 6-6. 관찰 - 병목은 한 층 안쪽으로 이동한다

두 오해를 걷어내고 나면, 같은 표에서 주목할 만한 현상이 하나 더 보입니다. 오해는 아니고, 측정 중에 부수적으로 드러난 관찰입니다. **가상 스레드를 켜는 순간 HikariCP 풀이 플랫폼 모드보다 더 깊이 차오릅니다.**

결과표에 HikariCP write-pool 활성 peak를 한 컬럼 더 얹어 보겠습니다.

| VU | 모드 | Tomcat | write-pool 활성 peak | 풀 상한 |
|---|---|---|---|---|
| 200 | 플랫폼 | 200 | 70 | 200 |
| 200 | 가상 | — | 124 | 200 |
| 400 | 플랫폼 | 400 | 176 | 200 |
| 400 | 가상 | — | 186 | 200 |
| 800 | 플랫폼 | 800 | **200 (상한)** | 200 |
| 800 | 가상 | — | **200 (상한)** | 200 |

VU 200에서 이미 가상 스레드가 플랫폼 스레드보다 풀에 더 깊이(70 → 124) 들어갑니다. 이유는 단순합니다. 플랫폼 모드에서는 Tomcat 워커 200개 중 소셜 경로(50 %)만 DB 커넥션을 쥐기 때문에 동시 DB 접근이 워커 수에 의해 자연히 묶이고, 가상 모드에서는 이 한도가 사라져 동시에 mock OAuth 응답을 받은 social 요청이 곧바로 DB를 두드립니다. VU 400에서는 플랫폼 쪽 Tomcat을 400으로 키운 덕에 격차가 줄고(176 vs 186), VU 800에서는 양쪽 모두 풀 상한 200을 찍으면서 커넥션 획득 대기가 30초 타임아웃으로 대량 발생합니다(플랫폼 47.6 %, 가상 31.3 % 에러). 플랫폼 스레드 쪽이 Tomcat 워커 수를 VU에 맞춰 키운 순간, 이전까지 Tomcat이 가려 주던 HikariCP 병목이 플랫폼 스레드에서도 똑같이 드러난 것입니다. **병목이 사라지는 게 아니라 한 층 안쪽으로 이동**합니다.

이건 측정 과정에서 직접 부딪혀 본 결과이기도 합니다. 초기 탐색 단계에서 HikariCP 풀을 부하 대비 작게 둔 채 가상 스레드 모드로 돌렸을 때, 두 가지 오류가 차례로 일어났습니다. 먼저 **커넥션 획득 대기 30초 타임아웃**이 대량으로 뜨고, 풀을 키웠더니 이번엔 **MySQL 쪽 커넥션 상한**에 걸리는 식이었습니다. 플랫폼 스레드 모드에서 Tomcat을 충분히 작게 두면 이 두 오류 모두 잘 안 납니다. Tomcat 워커 수가 그 다음 병목들을 가려 주고 있었기 때문입니다. 가상 스레드를 켜는 순간 DB 풀, MySQL 커넥션 상한, 외부 API 동시 호출 한계가 전부 새 천장 후보가 됩니다. **사이징해야 할 곳이 한 단계 안쪽으로 이동**할 뿐, 사라지지는 않습니다.

결국 HikariCP 풀 크기 자체가 뒷단 세마포어 역할을 합니다. 가상 스레드가 아무리 많이 만들어져도 DB 커넥션은 유한하고, 풀이 그 상한에서 30초 타임아웃으로 줄을 세웁니다. 가상 스레드는 이 줄을 없애 주지 않고, 앞에 늘어서는 일만 더 많이 만들어 냅니다. 풀 크기는 여전히 MySQL `max_connections`와 워크로드 패턴을 보고 직접 정해야 합니다.

### 6-7. 그럼 차이는 어디에 있나 ① - OS 스레드 수

여기까지 보면 "그래서 가상 스레드는 뭐가 좋은 건가" 싶은 의문이 생깁니다. 처리량도 p95도 같고, DB 사이징은 오히려 어려워지고, 무제한으로 만들 수도 없다면 말입니다. 차이는 처리량 컬럼이 아니라 자원 컬럼에 숨어 있었습니다.

결과표의 OS 스레드 컬럼만 뽑아 봅니다 (`/proc/$PID/status`의 `Threads:` 필드).

| VU | 플랫폼 | 가상 | 배수 |
|---|---|---|---|
| 200 | 249 | 49 | 5.1× |
| 400 | 449 | 49 | 9.2× |
| 800 | 847 | 49 | 17.3× |

- 플랫폼 스레드 쪽은 VU에 선형으로, OS 스레드 peak ≈ VU + 49(JVM 내부 스레드)입니다. VU가 두 배면 OS 스레드도 두 배입니다.
- 가상 스레드 쪽은 평탄해서, VU와 무관하게 49개입니다. carrier 4개(`-XX:ActiveProcessorCount=4`)에 GC, JIT, 프레임워크 내부 스레드를 더한 값입니다.

OS 스레드 하나가 줄면 뭐가 좋은가. 직접적으로는 두 가지입니다. 각 OS 스레드가 잡고 있는 커널 스택과 TCB 메모리가 줄고, 커널 스케줄러의 run queue에 올라 있는 엔트리가 적어져 스케줄링 결정이 가벼워집니다. 다만 이 측정 범위(정상 상태 기준 VU 400까지)에서는 그 효과가 눈에 띄게 나타나지 않았습니다. VmRSS는 두 모드가 비슷했고, 처리량과 p95도 같았습니다. OS 스레드 수 자체가 체감되는 게 아니라, 이 숫자가 다음에 볼 **비자발 선점의 증가 속도**에 영향을 미치는 쪽이 진짜 이득이었습니다.

참고로 가상 모드의 이 "49"는 **carrier 수(4)가 아닙니다.** `-XX:ActiveProcessorCount=4`에 맞춰 carrier는 4개지만, 나머지 45개가 JVM이 커널에 띄워 두는 상시 네이티브 스레드(GC 워커, C1/C2 컴파일러, VM/시그널/참조 핸들러, 프레임워크 내부 스레드)입니다. carrier만 따로 보고 싶다면 JFR이나 jstack에서 `ForkJoinPool-1-worker-*` 이름을 직접 찾아야 합니다.

### 6-8. 그럼 차이는 어디에 있나 ② - 비자발 선점(nonvol)

"OS 스레드가 9배 적으니 커널 스케줄러 비용도 그만큼 적지 않을까"는 자연스러운 기대지만, 이 비교에서 중요한 건 **자발 양보가 아니라 비자발 선점**입니다. 같은 "컨텍스트 스위치"라도 두 종류는 성격이 다릅니다.

- **자발 양보 (voluntary yield)**: 스레드가 blocking I/O나 lock 대기에 들어가 "어차피 멈춰야 할 때" 스스로 CPU를 내놓는 전환입니다. 전환 비용은 있어도 논리적으로 낭비가 아닙니다. 워크로드가 하는 일의 일부입니다.
- **비자발 선점 (nonvoluntary preemption)**: 커널 스케줄러가 **아직 일하는** 스레드를 시간 슬라이스가 끝났다는 이유로 강제로 떼어내는 전환입니다. 그 순간 CPU 캐시(L1, L2, TLB)는 다음 스레드의 워킹셋으로 교체되면서 따뜻해져 있던 캐시 라인이 버려지고, 레지스터 저장/복원과 스케줄러 의사결정 비용까지 붙습니다. **같은 처리량을 내는 데 CPU 시간이 캐시 냉각과 스케줄링 오버헤드로 빠져나가는 상태**, 이게 "커널 스케줄러 비용"이 가리키는 실체입니다.

그러니 두 모드를 비교할 때 봐야 할 건 총 스위치가 아니라 비자발 선점입니다. 결과표에서 `nonvoluntary_ctxt_switches`만 따로 뽑아 봅니다 (`/proc/$PID/task/*/status`를 180초 정상 상태 구간 동안 모든 태스크에 걸쳐 합산한 값).

| VU | 플랫폼 nonvol/s | 가상 nonvol/s | 플랫폼 대비 가상 |
|---|---|---|---|
| 200 | 1,324 | 783 | −41 % |
| 400 | 7,168 | 1,670 | **−77 %** |

- **모든 VU 레벨에서 가상 스레드 쪽이 플랫폼보다 비자발 선점이 적습니다.** VU 200에서 이미 41 % 적고, VU 400에서는 77 % 적습니다.
- VU를 두 배로 키우면(200 → 400) 플랫폼 쪽은 **+5,844/s(5.4배)** 늘어나고, 가상 쪽은 **+887/s(2.1배)**만 늘어납니다. 절대 증가 폭이 약 1/6 수준입니다.

플랫폼 스레드 쪽은 400개 Tomcat 워커(+ JVM 베이스라인 49개)가 4개 코어를 나눠 쓰면서 커널 스케줄러가 끊임없이 시간 슬라이스를 끊고 다른 워커를 올려야 했고, 가상 스레드 쪽은 선점 대상이 carrier 4개뿐이라 VU가 늘어도 이 비용이 크게 붙지 않습니다. 결국 **비자발 선점의 상한을 VU가 아니라 carrier 수가 정합니다.**

정리하면 "OS 스레드 수가 9배 적다"는 사실의 진짜 이득은 컨텍스트 스위치 총량이 아니라 **비자발 선점의 절대량과 증가 속도를 동시에 눌러 준다는 것**입니다. 플랫폼 스레드를 부하에 맞춰 키우면 처리량과 응답 지연은 가상 스레드와 같아지지만, 그 대가로 커널 스케줄러가 더 많은 선점 비용(그리고 캐시 냉각 비용)을 떠안습니다. 가상 스레드는 이 대가를 내지 않습니다. 이 측정 범위(정상 상태 기준 VU 400까지)에서는 처리량과 p95 차이로는 드러나지 않았지만, 부하가 더 커져서 선점 폭증 구간이 길어질수록 이 차이는 헤드룸, 전력 소비, 공평성 측면에서 벌어지게 됩니다.

> **가상 스레드의 실질적 이득을 "컨텍스트 스위치를 줄인다"로 요약하면 자발 양보까지 함께 세는 오류가 생깁니다.** 자발 양보는 워크로드가 하는 일의 일부이지 오버헤드가 아니고, 가상 스레드는 오히려 이쪽을 자기 몫으로 더 떠안습니다. 같은 I/O 지점에서 플랫폼 스레드는 OS 스레드가 한 번 block되고 끝이지만, 가상 스레드는 park, carrier 반납, 다음 가상 스레드 mount까지 carrier 위에서 일어나는 모든 전환이 voluntary switch로 잡히기 때문입니다. 정확히 말하면 **"비자발 선점의 절대량과 증가 속도를 풀 크기 대신 carrier 수로 묶어 둔다"**, 이게 가상 스레드가 커널 스케줄러에 덜 걸리는 진짜 이유입니다.

### 6-9. 그래서 뭐가 좋은가

앞의 두 절을 한 줄로 묶으면 이렇습니다. **가상 스레드는 더 빠른 것도, 메모리를 덜 쓰는 것도 아닙니다.** 이 측정 범위(정상 상태 기준 VU 400까지)에서는 VmRSS도, 처리량도, p95도 두 모드가 비슷했습니다. 남는 차이는 단 하나입니다. **Tomcat 풀 크기를 트래픽에 맞춰 예측할 필요가 없다는 것**, 그리고 그 덕분에 **비자발 선점 비용이 풀 크기에 따라 커지지 않는다는 것**입니다.

운영 트래픽은 시간대마다 변합니다. 점심 피크, 새벽 트래픽, 이벤트가 쏟아질 때까지 Tomcat 풀은 이 전부를 커버할 수 있게 미리 정해 둬야 하고, 너무 작으면 처리량이 풀 크기에 막히고(앞서 Little's Law로 본 그 상한), 너무 크면 비자발 선점이 폭증합니다. 어느 쪽도 공짜가 아니고, 이건 "내일 트래픽이 어떻게 생길지"를 먼저 맞춰야만 풀리는 숙제입니다. 가상 스레드는 carrier 수(= `ActiveProcessorCount`)를 고정해 이 **입구 사이징** 하나를 없앱니다.

여기서 한 가지를 분명히 해야 합니다. 이게 "사이징을 전부 안 해도 된다"는 얘기는 아닙니다. 정확히 반대입니다. DB 풀과 MySQL `max_connections`, FCM 동시 발송 수, Playwright 동시 실행 수 같은 **뒷단 자원 상한**은 가상 스레드를 쓰든 플랫폼 스레드를 쓰든 똑같이 세마포어/풀 크기로 막아 둬야 하는 일입니다. 이 프로젝트의 가상 스레드 경로에도 이 세마포어들은 그대로 붙어 있고, 플랫폼 스레드 위에서 같은 일을 했어도 똑같이 붙어 있었을 것입니다. 차이가 있다면 사이징의 **성격**입니다. Tomcat 풀 크기는 들어오는 트래픽 모양을 미리 맞춰야 푸는 숙제였고, 뒷단 세마포어는 "FCM이 허용하는 rps가 얼마냐", "MySQL `max_connections`가 얼마냐" 같이 **상대 자원이 이미 갖고 있는 숫자를 베껴 적는** 쪽에 가깝습니다. 가상 스레드가 없애 주는 건 **앞쪽 하나**입니다.

이 프로젝트가 처음부터 가상 스레드 위에 올라탄 이유가 그래서입니다. FCM 발송, 스크래핑, 스케줄러가 동시에 도는 시간대의 동시성 패턴을 **미리 계산해서 Tomcat 풀에 박아 넣는 일**을 하고 싶지 않았고, 뒷단 세마포어는 어차피 세워 둘 작정이었기 때문입니다. "빨라지기 위해"가 아니라 **"트래픽 예측을 해야만 풀리는 입구 사이징을 통째로 뺀다"**, 이것 하나입니다.

## 마치며: 왜 플랫폼 스레드가 아니라 가상 스레드였나 (로컬 실험 한정)

가상 스레드 위에서 프로젝트를 설계한다는 건 `spring.threads.virtual.enabled=true` 한 줄로 끝나지 않았습니다. 스케줄러 설정, ThreadLocal 대신 ScopedValue 선택, 자식 스레드 컨텍스트 전파까지, **코드베이스를 처음부터 가상 스레드 친화적으로 맞춰 두는 작업이 본 게임**이었고, 그 작업의 정당성은 측정으로만 확인할 수 있었습니다.

측정을 거치고 나니 처음 기대했던 "두 배 빨라짐" 같은 숫자는 전부 허물어졌습니다. Tomcat 풀을 부하에 맞춰 키우면 처리량도 p95도 두 모드가 같았고, VmRSS도 다르지 않았습니다. DB 사이징은 오히려 한 계단 안쪽으로 옮겨왔고, "경량이니 무제한"도 park continuation과 속도 조절 신호 소실 앞에서 무너졌습니다. 뒷단 자원 상한들(DB 풀, MySQL `max_connections`, FCM 발송 세마포어, Playwright 동시 실행 수)은 **양쪽 모드 모두 동일하게** 세워 둬야 하는 일이라, "가상 스레드가 이 상한들을 드러내 준다" 같은 말도 사실이 아닙니다. 그 상한들은 플랫폼 스레드 위에서도 원래부터 거기에 있었습니다.

한 가지 더 분명히 해야 합니다. **가상 스레드가 "서버가 안 죽게 해 주는" 것도 아닙니다.** 가상 스레드 모드에서도 트래픽 예측 없이 입구를 열어 두면 서버는 죽습니다. OS 스레드 폭증 대신 힙 고갈(park된 continuation, 요청 객체, HikariCP 대기 큐)이나 뒷단 연쇄 장애(풀 타임아웃 → 재시도 폭증)로 무너지고, Tomcat의 `server.tomcat.max-connections`(기본 8192)는 가상 스레드 모드에서도 여전히 accept 레벨의 하드 캡으로 남아 있습니다. **죽음의 가능성은 그대로고, 트리거가 바뀔 뿐입니다.**

그런데도 이 프로젝트는 처음부터 가상 스레드 위에 올라탔습니다. 이유는 "안 죽는다"가 아니라 **사이징 숙제의 성격이 바뀐다**는 것입니다.

플랫폼 스레드 모델에서 `maxThreads`는 **빼는 선택지가 없는 필수 사이징**입니다. 요청 하나가 OS 스레드 하나를 1:1로 점유하기 때문에, 이 숫자를 막지 않으면 스파이크 구간에서 OS 스레드가 커널 상한까지 늘어납니다. 그래서 반드시 값을 정해야 하는데, 그 값이 **트래픽 예측에만 의존합니다.** 너무 작으면 처리량이 풀 크기에 막히고(6-4의 Little's Law 상한), 너무 크면 비자발 선점이 폭증합니다(6-8). 둘 다 실측한 현상이고, 둘 다 "내일 트래픽이 어떻게 생길지"에 대한 베팅의 결과입니다. 뒷단 세마포어가 "이 자원이 몇이냐"로 정해지는 트래픽 무관 상수라면, `maxThreads`는 **트래픽 모양이 바뀔 때마다 다시 맞춰야 하는, 그리고 맞추지 않는 선택지가 없는** 유일한 숫자입니다.

가상 스레드는 이 한 줄을 **예측 무관 상수로 대체합니다.** `spring.threads.virtual.enabled=true`를 켜면 Tomcat의 `maxThreads`는 사실상 무의미해지고(요청마다 새 가상 스레드를 만들어 주니까요), 입구의 하드 캡 역할은 `maxConnections`(기본 8192)가 이어받습니다. 이 숫자는 "내일 트래픽이 얼마냐"가 아니라 "힙, FD, 뒷단이 버틸 만한 충분히 큰 수"로 한 번 잡고 거의 안 건드리는 **예측 무관 상수**입니다. 그 안쪽의 실제 동시성 상한은 이미 있던 뒷단 세마포어들이 각자 자기 용량으로 막아 줍니다. 이들도 양쪽 모드 모두 필요했던 것이라 가상 스레드가 "새로 해 준 일"에 들어가지도 않습니다.

가상 스레드가 순수하게 해 준 일은 딱 하나, **플랫폼 모델에서 빼는 선택지가 없던 "트래픽 예측 기반 필수 사이징(`maxThreads`)"을, "예측 무관 상수(`maxConnections` 기본값 + 뒷단 세마포어)"로 대체해 준 것**입니다. 죽음의 가능성도, 죽음의 개수도 줄여 주지 않습니다. 줄어드는 건 **"내 트래픽 예측이 얼마나 정확한가"에 걸려 있는 사이징 한 줄**입니다.

정리하면 이 프로젝트가 플랫폼 스레드가 아니라 가상 스레드를 택한 근본적인 이유는 한 줄입니다.

> **플랫폼 스레드 모델의 `maxThreads`는 빼는 선택지가 없고, 그 크기는 트래픽 예측으로만 정해집니다. 가상 스레드는 이 한 줄을 예측 무관 상수로 대체합니다. 서버가 안 죽게 해 주는 것도, 자원을 아껴 주는 것도 아니지만, 트래픽 예측에 걸려 있는 사이징 한 줄만큼은 통째로 빠집니다.**

"더 빨라서"도 아니고, "자원이 적게 들어서"도 아니고, "서버가 안 죽어서"나 "뒷단 사이징을 안 해도 돼서"는 더더욱 아닙니다. **트래픽 예측에 의존하는 필수 사이징 한 줄을 예측 무관 상수로 바꾸고 싶었다**, 이 프로젝트의 가상 스레드 선택은 그것 하나로 설명됩니다.

단, 한 가지를 다시 분명히 해 둡니다. **이 결론의 숫자 근거는 전부 로컬 실험입니다.** 스레드 모델 차이만 분리하려고 병목이 아닌 쪽을 전부 눌러 둔 환경이라, 여기서 나온 값은 모드 비교용이지 운영 사이징 값이 아닙니다. 같은 논리가 운영과 동일 스펙, 운영 데이터 분포 위에서도 성립하는지, 그리고 외부 세마포어와 `max-connections`의 실제 운영 값을 점진적 RPS 측정으로 어떻게 확정했는지(무한정 생성이 만든 두 군데의 리소스 한계를 운영 인프라에서 실측해 막은 트러블슈팅)는 [“가상 스레드는 마음껏 만들어도 된다”, 운영에서 곧이곧대로 믿으면 생기는 일]({{< ref "5.md" >}}) 글에서 수치로 잇습니다.
